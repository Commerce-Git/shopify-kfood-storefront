# Gemini 작업 지시 — 프런트엔드 점검 후속 조치

> **상태: 과거 작업 지시 보존본.** 아래 항목은 이전 점검의 수정 후보이며 이번 플랫폼 목표·문서 정리 작업의 실행 지시가 아니다. 새 요청이 들어오면 [공통 기준](../docs/platform-analysis/README.md)과 현재 코드를 대조해 적용할 항목을 새 실행 지시로 작성한다. 이 표시는 실행기 잠금이나 과거 작업 완료 판정이 아니다.

## 목표

Blank Seoul 스토어프런트에서 확인된 보안·정합성 문제를 코드에서 재확인하고 수정한다. 작업이 끝나면 `.agent-bridge/REPORT.md`에 실제 수행 결과를 기록한다.

## 작업 범위와 우선순위

1. **작가 팔로우 API의 본인 확인**: `app/api/artists/follow/route.ts`의 POST/GET이 요청자가 제시한 이메일을 그대로 사용한다. 타인의 이메일로 Shopify 고객 태그와 마케팅 수신 상태를 변경하거나 팔로우 목록을 조회할 수 없도록 한다. 비로그인 사용자의 팔로우 경험이 필요하다면 서버에서 소유권을 검증할 수 있는 흐름을 설계하고 구현한다. 마케팅 수신 동의를 팔로우 동작만으로 임의 변경하지 않는지 확인한다.
2. **리뷰 쿠폰의 중복 발급과 부분 실패**: `app/api/review/route.ts`의 토큰 확인 → Shopify 쿠폰 생성 → Supabase 저장 흐름에서 동시 요청 및 각 단계 실패를 처리한다. 한 리뷰에 하나의 유효한 보상만 남도록 하고, Shopify GraphQL 최상위 오류·mutation `userErrors`·결과 누락을 확인한다. 재시도 시에도 중복 쿠폰이 만들어지지 않도록 한다.
3. **주문 취소 응답**: `app/api/cancel-order/route.ts`의 실패 응답에서 내부 `debug` 데이터를 제거하고 고객에게 표시하는 주문번호는 서버에서 조회한 값을 사용한다.
4. **자동화 일정 확인**: `vercel.json`의 빈 `crons`와 `OPERATIONS.md`의 일정이 다른 이유를 확인한다. 이 저장소에서 관리하는 일정이라면 설정과 문서를 일치시킨다. 외부 스케줄러가 담당한다면 확인 가능한 근거와 운영 경로를 문서에 적는다. 배포 환경의 설정을 확인할 수 없다면 추측하지 말고 미확인으로 보고한다.
5. **문서 정합성**: 현재 공예품 카탈로그와 취소 가능 시간의 실제 설정에 맞춰 `README.md` 및 `OPERATIONS.md`의 오래된 설명을 정리한다. 확정되지 않은 사업 정책은 임의로 결정하지 않는다.

## 구현 및 검증 기준

- 이 저장소의 `AGENTS.md`를 따르고, Next.js 코드를 수정하기 전에 `node_modules/next/dist/docs/`의 관련 가이드를 읽는다.
- 기존 고객 흐름을 유지하면서 권한 검증은 서버에서 수행한다. 검증 실패 시 Shopify Admin API나 Supabase service role 쓰기를 실행하지 않는다.
- 보안 경계, 동시 요청, 실패 후 재시도에 관한 의미 있는 테스트를 추가하거나 갱신한다.
- `npm run typecheck`, `npm run test:unit`, `npm run lint`, `npm run build`를 실행한다. 기존 린트 오류가 남으면 이번 변경으로 생긴 오류와 기존 오류를 구분해 보고한다.
- 외부 서비스에 실제 이메일 발송, 쿠폰 발급, 주문 취소 같은 실거래 동작을 시험할 때는 테스트 환경과 대상을 먼저 확인한다.
