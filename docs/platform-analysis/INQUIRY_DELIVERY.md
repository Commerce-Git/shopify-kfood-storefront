# 문의 알림의 연결 범위와 사용량 검토

2026-09-30 검토. 고객지원 M10-F001, 인증 M01, 전달 M11, 운영 M12와 계약 C09/J04, 목표 R07/R09/R10에 연결한다.

현재 단계는 **무료 테스트 환경에서 불필요한 조회를 줄이는 간단한 개선**이다. 고객이 없는 상태에서 상세 비용 분석을 더 늘리지 않고 닫힌 문의창의 조회 간격, 탭 숨김/복귀와 오류 재시도를 보완했다. 로컬 브라우저에서 변경 전후를 확인했으며 운영 배포·비용 절감·부하 수용량은 검증하지 않았다. 참여자별 실시간 알림은 후속 후보로 유지한다.

운영 방향과 단계 조정의 원본은 [목표 문서 D020/D021](PROJECT_DIRECTION.md#결정-기록)이다. 즉시 상담을 약속하지 않고, 접속 중 답변 도착 알림과 대화 이어보기를 우선한다. 구체적인 연결 수명·인증 방식·시험 수치는 아래의 설계 제안이며 구현 완료를 뜻하지 않는다.

## 확인된 사실과 미확인 자료

- 사용자 확인: Vercel과 Supabase 모두 무료 사용 중. 실제 계정의 팀/조직, 프로젝트별 사용량, 적용된 한도는 원격 조회하지 않았다.
- 코드 기준: storefront `a3042e0`, admin `890007a`. 기존 문서 미커밋 변경을 보존했다.
- 공식 자료 확인일은 2026-09-30이다. 요금제 표의 수치를 현 계정 청구서나 배포 설정 확인으로 취급하지 않는다.
- 기존 정산 시험 데이터는 메시지 부하를 대표하지 않는다. 문의 수·메시지 길이·첨부 수·접속 시간을 별도로 측정해야 한다.

고객 브라우저 → Storefront 문의 프록시 → Admin 문의 API → Supabase 순서다. 정상 배포에서 고객 GET 하나가 두 앱의 동적 함수 실행으로 이어진다. 로컬 개발 서버 요청 자체가 Vercel 호출료를 발생시키는 것은 아니다.

작가 플로팅 메신저는 [대시보드](../../../blank-seoul-admin/app/artist/dashboard/page.tsx)에서 열린 동안 마운트한다. 모든 작가 방문자가 항상 문의 연결을 보유한다고 계산하지 않는다. 작가 thread 이벤트의 화면 필터는 수신 후 실행되므로 실제 서버 RLS가 송신 범위를 제한하는지 확인해야 한다. 이번 분석은 데이터 유출 여부를 확정한 보안 감사가 아니다.

현재 성공 GET은 읽기 경로다. DB SELECT 횟수가 그대로 디스크 읽기 횟수나 건당 과금은 아니다. 실제 IO·CPU·캐시 적중·전송량과 함께 해석한다.

## 비교용 요청량 계산

아래는 최초 검토 당시의 산술 비교다. 표의 현재는 수정 전 코드를 뜻하며, 15초 개선 폴링과 실시간 수치는 구현안이 아닌 가정이다. 실제 적용은 열림 10초 / 닫힘 60초이고 짧은 확인 결과는 아래 기록을 따른다. 운영 예측이 아닌 동일 조건의 산술 비교다. 하루 문의 토큰 보유 방문 세션 D개, 월 30일, 세션당 보이는 시간 30분을 가정한다. 그중 대화창은 5분 열고 25분 닫는다. 세션 수는 고유 고객 수와 다르며 숨겨진 탭 시간은 제외한다.

- 현재: 정기 조회 30 × 60 / 10 = 180회 + 최초 1회 + 열기 1회 = **182회/세션**.
- 개선 폴링 제안: 열림 15초 간격 20회 + 닫힘 60초 간격 25회 + 최초/열기 2회 = **47회/세션**. 닫힌 창 알림에는 최대 약 60초와 네트워크 지연이 생긴다.
- 실시간 제안: 최초/열기/복구 조회 각 1회 + 새 알림 후 필요한 조회 3회 + 연결 자격 발급/갱신 2회 = **8회/세션**. 자격 API도 같은 프록시 경로를 가정한다. 실제 재연결·권한 갱신 빈도에 따라 증가한다.

| 하루 해당 세션 | 현재 월 고객 HTTP | 개선 폴링 월 고객 HTTP | 실시간 월 고객 HTTP | 현재 두 앱 함수 합계 | 실시간 두 앱 함수 합계 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100 | 546,000 | 141,000 | 24,000 | 1,092,000 | 48,000 |
| 1,000 | 5,460,000 | 1,410,000 | 240,000 | 10,920,000 | 480,000 |
| 10,000 | 54,600,000 | 14,100,000 | 2,400,000 | 109,200,000 | 4,800,000 |

함수 합계는 고객 HTTP × 2다. 메시지 전송·문의 생성·읽음 쓰기·운영자/작가 API·오류 재시도·첨부 다운로드·다른 페이지·미들웨어 추가 실행은 위 비교에 포함하지 않았다. 실시간 알림 자체는 브라우저와 Supabase 사이로 보내며 Vercel에 장시간 연결을 유지하는 설계가 아니다. 8/182에서 계산한 약 95.6% 감소는 이 가정의 요청량 감소이며 실측·전체 청구액 감소율이 아니다.

D=1,000이면 현재 문의 조회에서 월 약 1,092만 SELECT 요청이 발생한다. 실시간 시나리오에서 데이터 조회 6회에 기존의 2 SELECT 구조를 유지하면 월 36만 SELECT 요청이다. 자격 발급·채널 권한 확인·안 읽은 요약·이벤트 발행·읽음 및 메시지 쓰기는 추가해야 한다. DB 행 수·IO 절감률은 이 횟수만으로 확정하지 않는다.

전송량도 따로 잰다. 예를 들어 D=100에서 DB→Admin 실제 응답이 평균 20 KB라면 546,000 × 20 KB = 월 10.92 GB다(십진 단위, 압축/헤더 제외). 평균 20 KB는 가정이며 현재 측정값이 아니다. 서버 간 응답과 브라우저 응답은 형태·압축·과금 구간이 달라 하나의 바이트 수를 모든 업체에 적용하지 않는다.

## 연결과 알림의 범위 제안

| 사용자 상태 | 연결 | 읽기 동작 |
| --- | --- | --- |
| 문의 없는 방문자 | 문의용 연결 없음 | 문의 조회 없음 |
| 보이는 탭에서 유효한 진행 중 문의 또는 미확인 답변 보유 | 해당 참여자의 알림 연결 유지 | 창이 닫혀 있으면 요약/배지만 갱신. 답변마다 전체 대화 재조회하지 않음 |
| 대화창 열림 | 같은 연결 재사용 | 최근 30–50건, 새 변경분, 이전 기록 요청 시 페이지 조회 |
| 만료 또는 종료되어 미확인 답변도 없는 문의 | 초기 상태 확인 후 닫힌 창의 연결 해제 제안 | 다시 열 때 권한·상태 재확인 |
| 숨겨진 탭·오프라인 | 짧은 유예 후 문의 구독 해제 제안 | 복귀 시 재구독 완료 후 변경분 대조 |
| 관리자·작가 | 업무 중 본인 권한의 알림과 선택 대화 | 모든 고객에게 업무 이벤트를 보내지 않음 |

다른 기능이 같은 소켓을 쓰는 경우 문의 채널만 정리하고 공유 소켓 전체를 끊지 않는다. 여러 채널이 한 소켓을 공유할 수 있고 여러 탭은 소켓을 늘릴 수 있으므로, 방문자 수·대화 수·채널 수를 곧바로 연결 수로 환산하지 않는다.

예를 들어 고객 소켓 60 + 관리자 5 + 작가 30 + 다른 기능에서 별도로 열린 소켓 20 = 같은 시점 115개다. 고객이 160개라면 합계 215개로 Free의 200 연결 한도를 넘는다. 이 수는 가정이다. 연결 예산은 고객뿐 아니라 현재 업무 구독도 포함하며 전체 20,000명 방문 목표를 20,000개 문의 연결로 구현하지 않는다.

메시지 비용의 단위도 고객이 입력한 채팅 한 건과 다르다. Broadcast는 발신 1건 + 수신 소켓 수로 센다. 예를 들어 월 30,000세션에 공개 변경 이벤트가 세션당 4개, 이벤트당 수신자가 평균 2개라면 30,000 × 4 × (1 + 2) = 월 360,000건이다. 이는 수신 3건·본인 발신 관련 1건 등의 예시일 뿐이다. 번역 완료·상태 변경·별도 운영 채널 발행·기존 Postgres Changes·재전달·다중 탭은 추가한다. [공식 메시지 집계](https://supabase.com/docs/guides/platform/manage-your-usage/realtime-messages)

4만 이벤트를 100명 전체에게 보내면 약 404만 건이 된다. 대화/참여자별 전송과 서버 권한 검사가 비용과 정보 격리 모두에 중요하다. 클라이언트가 수신 후 걸러내는 구조로 대체하지 않는다.

## 구현 전에 확정할 계약

1. 기존 API와 DB를 메시지 원본으로 유지한다. 알림에는 참여자에게 공개 가능한 변경 식별자·버전 등 최소 정보만 넣고, 내부 작가 중계 이벤트를 고객 채널에 발행하지 않는다.
2. 게스트 문의 토큰을 그대로 공개 채널 이름으로 쓰지 않는다. 토큰 검증 후 대화 범위를 제한하는 실시간 자격과 private channel RLS를 설계한다. 일반 회원 로그인과 게스트 접근을 함께 시험한다. 익명 Auth 도입 여부는 미결정이며 방문자 전원 익명 계정 생성으로 시작하지 않는다.
3. 채널 권한은 연결/JWT 갱신 때 검사되므로 회수·만료 후 기존 연결의 수명도 정해야 한다. 수신 후 화면 필터만으로 권한을 보장하지 않는다. [Realtime 인증](https://supabase.com/docs/guides/realtime/authorization)
4. 재연결 시 DB 변경분을 대조한다. 단순 created_at 이후 조회는 이전 메시지의 번역·수정·삭제를 놓칠 수 있어 변경 버전 또는 별도 대조 계약이 필요하다. 알림과 조회 사이 경합, 역순 수신, 중복 전송을 시험한다.
5. 읽음은 실제 표시한 범위까지 저장하며 본인 메시지·내부 메시지를 고객 미확인 수에 더하지 않는다. 첨부 URL은 표시 대상과 만료에 맞춰 발급한다.
6. 정상 연결 중 정기 전체 조회를 중단한다. 끊긴 동안에만 간격을 늘리는 재조회와 단일 진행 요청을 사용하고, 재연결이 몰리지 않게 지연을 분산한다. 누락 대조 주기는 시험 후 정한다.

### DB 설정 진단

[inspect-inquiry-baseline.sql](../../../blank-seoul-admin/scripts/performance/inspect-inquiry-baseline.sql)을 Supabase SQL Editor에서 사용자가 직접 실행한다. `BEGIN TRANSACTION READ ONLY`와 10초 제한을 사용하고 끝에서 `ROLLBACK`한다. 실패 시 같은 에디터의 열린 트랜잭션을 `ROLLBACK;`으로 정리한 뒤 원인을 확인한다. 한도를 늘려 무작정 반복하지 않는다.

출력은 문의 테이블·Realtime 메시지 테이블의 존재, RLS 여부, SELECT 권한, 정책의 해시/단순 true 조건 여부, publication, 추정 행 수, 첨부 bucket 공개 여부다. 고객 행·토큰·정책 본문을 출력하지 않는다. `literal_true_using=false` 또는 RLS 활성화만으로 참여자 격리가 검증되지는 않는다. 이 SQL은 현재/최대 소켓 수나 API 호출 수를 대신 측정하지 않는다.

사용자가 실행한 테스트 DB 결과(2026-09-30 11:03:53 UTC): `inquiry_threads`/`inquiry_messages`는 RLS 활성, anon/authenticated SELECT 권한 없음, 정책 0개, Realtime publication 포함이었다. `realtime.messages`에는 정책이 없었고 첨부 bucket은 비공개였다. 익명 REST HEAD도 각 401이었으며 서비스 역할의 테스트 문의 조회는 200이었다.

이 결과는 직접 공개 읽기 차단과 현재 설정의 관찰이다. 일반 로그인 사용자용 Postgres Changes 구독에 필요한 읽기 권한/정책이 없고, 신규 private Broadcast 참여자 정책도 아직 준비되지 않았다. publication 등록만으로 알림 수신이 가능하다고 판단하지 않는다. 정책을 공개로 열어 해결하지 않으며 운영 DB의 동일성·전체 API 참여자 격리 검증은 별도다. 진단 시 추정 행 수 0은 정확한 행 수가 아니다. 이후 사용자가 가상 대화 2개와 각 메시지 2개를 준비한 결과를 제공했다.

### 브라우저 요청 측정

아래 10분 HAR 절차는 추가 측정이 필요할 때 사용하는 방법이다. 이번 변경에서는 로컬 브라우저 30초/1분 비교를 수행했으며 사용자에게 별도 HAR 제출을 요구하지 않는다.

1. 테스트 Storefront에서 기존 테스트 문의를 연다. 실제 주문·메일·작가 전달을 새로 발생시키지 않고 읽기 동작부터 측정한다.
2. DevTools Network에서 기록을 켜고 이전 요청을 비운다. 각 상태를 따로 10분 기록한다: 창 닫힘 `closed`, 창 열림 `open`, 다른 탭으로 이동 `hidden`, 연결/탭 복귀 포함 `reconnect`. 타이머로 실제 시간을 재고, 같은 기간 내 상태를 혼합하지 않는다. 테스트 중 문의 토큰이 만료되지 않았는지도 확인한다.
3. 각 상태에서 기록을 멈춘 다음 HAR로 저장한다. `Export HAR (sanitized)`를 사용할 수 있다. 이 옵션도 URL의 문의 토큰과 응답 본문까지 모두 제거하지는 않으므로 원본은 저장소 밖 `/tmp/`에 두고, 공유할 때는 다음 도구의 집계 결과만 사용한다. [Chrome HAR 설정](https://developer.chrome.com/docs/devtools/settings/preferences/)
4. Admin 프로젝트에서 아래 명령을 실행한다. `--origin`은 그 HAR를 기록한 브라우저 페이지의 정확한 origin으로 바꾼다. `--minutes`와 `--phase`는 자동 감지가 아니라 기록자가 입력하는 측정 조건이다.

```sh
node scripts/performance/inquiry-http-report.mjs \
  --input /tmp/inquiry-closed.har \
  --origin https://blank-seoul-storefront-git-dev-thec9rqwer-4072s-projects.vercel.app \
  --minutes 10 \
  --phase closed > /tmp/inquiry-closed-summary.json
```

[집계 도구](../../../blank-seoul-admin/scripts/performance/inquiry-http-report.mjs)는 외부 요청·환경 파일 로딩·로그인 없이 로컬 HAR를 읽는다. 정확히 일치하는 origin의 문의 API만 모아 요청 수/분당 횟수, 응답 코드, 성공 및 전체 소요 시간, 응답 바이트, 겹친 요청 수를 출력한다. 토큰·호스트·쿼리·헤더·본문은 출력하지 않는다. 음수나 누락된 바이트는 0으로 취급하지 않고 미확인 표본으로 센다.

HAR의 바이트는 네트워크 내보내기 도구가 제공하는 본문/압축 해제/전송 크기를 구분해서 표시한다. 브라우저 호출 수가 서버 함수 실행/DB SELECT 수와 같다는 뜻은 아니다. WebSocket 과금량·현재 소켓 수·저장 완료부터 화면 반영까지의 지연도 HAR만으로 확정할 수 없다. 0건 결과는 요청이 없었을 수도, 잘못된 origin/필터/기록 중지 때문일 수도 있다.

수정 전 코드는 보이는 탭에서 10분 동안 창 열림/닫힘 모두 약 60회 정기 조회가 예상됐다. 수정 후에는 정상 상태의 열린 창은 10초, 닫힌 창은 60초 간격이며 응답 완료 뒤 예약한다. 최초 조회·열기·진행 중 요청과 타이머 스케줄 때문에 경계에서 차이가 난다. 숨긴 상태에서는 이미 시작된 요청을 제외한 정기 조회가 멈춰야 한다. 이 예상과 다른 결과부터 원인을 확인한다.

### 실시간 소규모 시험의 진입 조건

기준 수치를 받은 뒤 한도 여유와 현재 참여자 권한을 판정한다. 신규 기능의 변경분 조회·게스트 실시간 자격·private 채널 권한·DB 변경 알림 계약을 먼저 구현/검증하고, 사용자가 테스트 DB SQL을 적용한 후 고객 두 명·관리자 한 명·필요한 작가 한 명으로 시험한다. 고객 간 격리, 내부 메시지 차단, 탭 복귀 시 누락 복구, 중복 전송, 안 읽은 수, 연결 정리를 확인한다. 현재 단계에서 이 시험을 완료했다고 판정하지 않는다.


## 무료 테스트 환경의 조회 개선 결과

2026-09-30 사용자 요청에 따라 먼저 폴링을 간소화했다. [조회 제어](../../lib/inquiries/polling.ts)는 열린 창 10초, 닫힌 창 60초 간격을 사용하며 숨김/오프라인 때 예약과 진행 중 브라우저 GET을 취소한다. 창 열기와 탭/네트워크 복귀 때 즉시 읽고, 반복 오류는 최대 120초까지 간격을 늘린다. 같은 문의의 GET이 진행 중이면 새 정기 요청을 시작하지 않는다. 문의 토큰이 없으면 제어기를 만들지 않는다.

| 브라우저 상태 | 각 관찰 기간 | 수정 전 GET | 수정 후 GET |
| --- | --- | ---: | ---: |
| 문의 없음, 보이는 탭 | 30초 | 0 | 0 |
| 대화 있음, 창 닫힘 | 60초 | 6 | 1 |
| 대화 있음, 창 열림 | 60초 | 6 | 6 |
| 대화 있음, 탭 숨김 | 60초 | 0 | 0 |
| 탭 복귀 후 열린 창 | 60초 | 6 | 6 |

1분 표본은 최초/창 열기 조회 뒤 준비 시간을 둔 정기 조회 비교다. 복귀의 즉시 조회도 준비 시간에 포함되어 표의 수에는 포함하지 않았다. 요청 완료 뒤 다음 타이머가 시작하므로 응답 시간과 관찰 경계에 따라 횟수가 달라질 수 있다. 닫힌 창의 6→1회는 이 조건에서 약 83.3% 감소이며 전체 Vercel 비용 절감률이 아니다. 열려 있을 때 답변 반영은 다음 조회와 네트워크 지연의 영향을 받는다. 닫힌 창의 정상 조회 간격은 60초이며 오류 중에는 최대 120초로 늘어난다. 네트워크 지연도 추가된다. 기존 미확인 배지 구현을 새로 완성한 변경은 아니다.

근거는 [민감값을 제외한 브라우저 비교 JSON](../../../blank-seoul-admin/scripts/performance/inquiry-polling-baseline.json)이다. 로컬 개발 서버 3001→3003→테스트 DB에서 가상 고객 1명의 대화 2메시지, 첨부 없음, GET만 확인했다. Chrome의 실제 다른 탭 전환으로 숨김을 확인했다. 운영 배포의 Vercel 호출·DB IO·청구 egress·메시지 저장부터 표시까지 지연은 측정하지 않았다. 단위 시험은 겹친 조회, 숨김/오프라인, 오류 지연/회복, 취소와 늦은 완료를 확인한다.

[데이터 준비 SQL](../../../blank-seoul-admin/scripts/performance/seed-inquiry-baseline.sql)은 사용자가 테스트 DB에 적용해 2대화/4메시지를 확인했다. 메일 알림 대상에서 제외하고 상품·주문·작가·첨부 연결을 만들지 않는다. 재시험이 끝나면 [정리 SQL](../../../blank-seoul-admin/scripts/performance/cleanup-inquiry-baseline.sql)을 사용자가 실행할 수 있다. 정리 SQL의 실제 실행은 이번에 하지 않았다.

다음은 변경을 커밋하고 사용자가 push한 뒤 Preview에서 같은 문의의 열기/닫기/복귀를 확인하는 것이다. 실시간 알림·변경분 페이지 조회·상세 비용 비교·요금제 전환은 실제 사용량과 운영 요구에 따라 별도로 선택한다.
