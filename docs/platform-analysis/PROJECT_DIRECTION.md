# BLANK SEOUL — 프로젝트 목적·운영 원칙·실행 계획

최종 업데이트: 2026-10-13 · 문서 버전: 0.62 · 단계: 외부 연동 시험 준비 · 일일 주문 알림 10,000명 모의 검증 · 배송 자동 복구 예약 보류

이 문서는 storefront와 admin을 하나의 서비스로 보고 관리하는 공통 기준 문서다. 대화에서 결정한 내용을 누적하고 개발 작업과 검증 결과를 연결한다. 현재 원본은 이 파일 하나이며, 다른 프로젝트에서는 복사본 대신 이 문서를 참조한다. 공유 문서 저장소로 이동한다면 원본 위치와 기존 링크를 함께 갱신한다.

현재 구현 근거·판정·개선 순서는 [플랫폼 분석 기준 문서](README.md)에서 확인한다. 운영 원칙은 이 문서가 원본이며, 분석 문서는 이를 검증하는 근거다.

**확정된 요구사항과 구현 완료는 다르다.** 아래의 확정은 사용자가 요구한 운영 원칙이라는 뜻이다. 현재 정적 전체 목록·핵심 경로 검토·기존 단위/타입 검사·물류 재현 시험을 수행했다. 전체 코드 보안 감사·운영 DB 진단·성능 검증을 완료한 것은 아니다.

**현재 HS 설계 방향(D060–D065):** 선정한20개 호별 등록 카테고리에서 원문 계층을 순서대로 선택해 한국 HSK·미국 HTSUS를 결정한다. 공통 소호와 국가별 세분을 연결하며 원문 부모·자식, 번호 없는 중간 조건, 기타, 최종 경로와 선택·수정·저장의 일치를 구현 완료 기준으로 삼는다. 원문 기타는 직접 선택한다. TEST 등록의20개 카테고리·63개 종류와 양국 원문 경로를 적용했고, 보류한 미국 가격 조건의 말단은 한국 코드·답변을 저장하면서 미국 코드를 확정하지 않는다. 상품 종류 이름에서 법적 사실을 추정하지 않는다. [Admin20개 호 계약](../../../blank-seoul-admin/doc/hscode/HS_CLASSIFICATION_DESIGN.md#hs20-registration)에 완료 증거·가격 대기·후속 범위를 기록한다.

**상품 분류 적합성의 후속 목표(D057):** 검토 대상 제품에 대해 제작자가 요구한 정보를 모두 확인한 사실대로 일관되게 답하면 근거 있는 HSK 하나가 결정돼야 한다. 필수 정보 부족이나 별도 판단이 남으면 해당 상품의 적합성 검증은 미완료이며 기타 기본값이나 임의의 대상 제외로 완료 처리하지 않는다. [Admin 후속 기준](../../../blank-seoul-admin/doc/hscode/HS_CLASSIFICATION_DESIGN.md#hs-complete-answer-criterion)을 따른다. 이 목표와 현재 원문 계층 선택 프로그램의 구현 완료 판정은 구분한다.

**후속 구현 관찰(2026-10-12):** 사용자의 다음 작업 진행 요청에 따라 에이전트가 가격 분기 없는4419 목재 식탁용품·주방용품을 확장 대상으로 선정했다. 현재4419 독립 등록 카테고리의8개 상품 종류에 원문 계층 선택을 연결하고 한국11개·미국8개 말단·14개 양국 경로를 검증했다. 구체적인 완료 증거와 TEST 적용 범위는 [Admin4419 등록 계약](../../../blank-seoul-admin/doc/hscode/HS_CLASSIFICATION_DESIGN.md#hs4419-source-selection)에서 관리한다. 이는 같은 원문 선택 방식을 다음 호에 적용한 구현이며 전체 식기 카테고리나 운영 DB의 전환을 확정한 정책은 아니다.

**20개 호 적용 관찰(2026-10-12):** 사용자 일괄 구현 승인으로20개 호·63개 종류에 공통 선택 화면·새18개 호 엔진과 기존4202·4419 엔진을 연결했다. 원문·92개 회귀·타입·변경 파일 린트·브라우저20흐름과 실제 TEST 임시 상품20개 저장/가격 수정/삭제를 확인했다. 이전 상품과 주문 스냅샷의 자동 변환·운영 DB·SQL·배포·외부 접수는 수행하지 않았다. 가격 검토 보류는 유지하며 실물 적합성은 D057 후속 목표다. 상세 증거는 [Admin 현재 계약](../../../blank-seoul-admin/doc/hscode/HS_CLASSIFICATION_DESIGN.md#hs20-registration)에서 관리한다.

**등록 입구 검토 관찰(2026-10-12):** 후속 사용자 승인으로20개 카테고리·63개 종류의 이름과 한정 범위를 원문에 대조했다. 인쇄 엽서, 식탁보·주방 수건, 섬유 커튼·실내 블라인드, 행주·빈 향낭·봉제 댕기 등 표시 이름을 구체화하고 단단한 머리띠·향료가 든 향낭을 구분했다. 선택한 입구·상품에만 안내를 표시한다. [Admin 현재 이름·근거](../../../blank-seoul-admin/doc/hscode/HS_CLASSIFICATION_DESIGN.md#hs20-entrance-review)를 따르며 원문 선택 답변·코드 규칙 변경과 구분한다.

**미국 원문 표시 보완 관찰(2026-10-12):** 후속 진행 승인으로20개 호 선택지의 한국어 표시와 기타 상위 조건을 보완했다. 원문 코드·계층·영어·가격 표시 정보를 유지하고 수치·단위·비교 조건을 검증했다. 관련53개 시험·타입·변경 파일 린트·브라우저20흐름과 모바일 상세 표시를 확인했다. [Admin 표시 번역 계약](../../../blank-seoul-admin/doc/hscode/HS_CLASSIFICATION_DESIGN.md#hs20-korean-labels)을 따르며 보류된 가격 조건의 확정이나 새 판단 규칙의 승인이 아니다.

**등록 순서 변경(2026-10-13):** 사용자 요청에 따라 작가 등록에서 카테고리를 고른 뒤 ‘다음’으로 해당 카테고리의 상품 종류를 선택한다. 이후 원문 HS 분류를 시작한다. 이전 이동과 선택 유지·카테고리 변경 시 초기화 계약은 [Admin 등록 입력](../../../blank-seoul-admin/doc/hscode/HS_CLASSIFICATION_DESIGN.md#hs20-registration)을 따른다.

## 1. 목적과 프로젝트 범위

**사용자가 동의한 궁극적 목표:** 작가가 창작과 판매량 결정에 집중하면서 안정적으로 판매·정산받고, 구매자는 원하는 상품을 신뢰하고 구매하며, 플랫폼은 감당 가능한 비용과 인력으로 이 거래를 반복·확장할 수 있게 한다.

**현재 사업 방향:** 한국 제조 상품으로 진행한다. K-Food는 통관과 작가 모집의 어려움 때문에 추후로 미뤘다. 이는 사용자가 설명한 사업 결정이며 통관 규정 자체에 대한 검증 결과는 아니다. K-Food 재개 시점과 조건은 미정이다.

**공개 상품 표현 기준(D031):** 플랫폼은 한국 제조와 한국 출고를 중심으로 소개한다. 모든 상품을 핸드메이드·수공예·장인 제작으로 홍보하거나 공장 제조 상품을 제외하는 문구를 사용하지 않는다. 실제 수작업 상품은 포함될 수 있으며, 해당 제조 방식은 근거가 확인된 개별 상품 특성으로 설명한다. 한국 브랜드·한국 디자인이라는 정보만으로 한국 제조를 보장하지 않으며, 제조·출고 원칙 확정과 실제 상품별 원산지 검증 완료를 구분한다. [공개 문구 검토·적용 기록](ORIGIN_COPY_AUDIT.md)에 수정 전 조사와 후속 로컬 구현·검증을 구분해 기록했다. 공통 문구와 Admin 생성 경로를 정리했으며 양쪽 앱 배포와 기존 상품별 제조 사실 확인은 남아 있다.

| 구분 | 현재 기준 |
| --- | --- |
| 우선 사업 범위 | 한국 제조 상품의 판매·주문 이행·정산을 중심으로 목표와 기능 우선순위를 평가 |
| 보류 사업 범위 | K-Food 및 그 판매를 전제로 한 전용 확장 작업. 재개 조건은 추후 결정 |
| 공통 기반 | 작가·상품·판매량·주문·물류·반품·정산·권한·운영 기능을 현재 상품 범위에 맞춰 검증 |
| 아직 결정할 것 | 우선 상품군·판매 국가·핵심 고객·한국 제조 확인 기준·입점 대상·수익 구조·성공 지표·예산 |

한국 제조 상품이라는 방향을 한국 브랜드 전체, 수공예품만, 또는 모든 비식품의 입점 허용으로 확대 해석하지 않는다. 기존 공급업체/발주 기능이 현재 모델에 필요한지도 별도로 판단한다.

Shopify 기반 프론트와 작가·운영 어드민을 통해 이 목표를 구현한다. 주문 시점의 거래 조건을 보존하고, 작가와 물류센터의 재고 책임을 구분하며, 두 프로젝트가 같은 데이터 정의를 사용하도록 한다. 동시 이용자 20,000명 목표는 확장성 요구로 유지한다.

| 구성 | 역할 | 현재 확인된 위치 |
| --- | --- | --- |
| 프론트 | Shopify 헤드리스 스토어프런트, 상품 탐색·구매·고객 서비스 | `blank-seoul-storefront` — 대화의 `blank-seoul-front`와 같은 프로젝트로 해석 |
| 어드민 | 작가 관리 페이지, 상품·재고·주문·정산 및 운영 관리 | 형제 폴더 `blank-seoul-admin` |
| Supabase | 프론트와 어드민이 공유하는 업무 데이터의 기준 저장소 | 사용자 설명상 `shopify-database`; 운영 설정은 미확인 |
| Shopify | 커머스 및 주문·결제 연동 | 데이터별 소유권과 동기화 범위를 별도로 명시 |
| 물류 시스템 | 물류센터 실물 재고와 입출고 사실 관리 | 실제 연동 방식·담당 시스템 확인 필요 |

한국 제조 상품이라는 큰 범위는 확정됐다. 핵심 고객, 판매 국가, 구체적인 상품 구성, 차별점, 수익 구조, 3개월 사업 목표는 후속 논의 대상이다. 기존 K-Food 단일 박스 전략은 보류 사업의 과거 자료로 참조하며 현재 상품·화면·운영 정책을 결정하는 기준으로 사용하지 않는다.

**다음 전략 작업 제안:** 합의한 목표에 성공 지표·필요 역량·모듈별 검증·구현 작업을 연결한다. 사업 측면에서는 우선 상품군을 고객의 구매 이유·모집 가능한 작가/공급자·배송과 반품 부담·주문당 비용·반복 판매 가능성으로 비교할 수 있다. 이는 제안이며 상품군 선정이 독립적인 플랫폼 분석의 선행 조건은 아니다. 아직 특정 상품군·시장·목표 수치를 확정하지 않았다.

### 역할별 목표 구체화 초안

구매자는 탐색·구매·배송 확인·취소/반품, 작가는 입점·상품/판매량 설정·주문 이행·정산, 물류 담당자는 실제 입고·검수·배정·출고, 운영자는 계정/상품/주문/정산 예외와 운영 상태를 관리한다. 실제 코드에는 별도 공급업체 발주 포털도 있어 사업 범위에 포함할지 확인해야 한다.

각 역할의 목표·현재 구현·미확인 부분·인수 기준 초안은 [사용자 여정](USER_JOURNEYS.md)에 연결했다. 기능 원본은 [모듈 지도](FEATURE_MAP.md), 데이터 변경 책임은 [데이터·흐름](DATA_AND_FLOWS.md)에서 관리한다. 출시 필수 기능과 사업 정책은 아직 사용자 합의가 필요한 항목을 별도 표시했다.

## 2. 요구사항 목록 — 사용자의 11개 고려사항

각 ID는 향후 작업 지시와 검토에서 사용한다. 검증 증거가 없는 항목은 구현 완료로 표시하지 않는다.

| ID | 사용자 항목 | 확정된 목표·원칙 | 현재 상태 / 필요한 검증 |
| --- | --- | --- | --- |
| R01 | 1 | 프론트는 Shopify 헤드리스 프로젝트다 | 구조 확인, 구매 흐름 전체 검증 필요 |
| R02 | 2 | 어드민은 작가 관리 및 정산을 담당한다 | 관련 문서 확인, 권한별 실제 흐름 검증 필요 |
| R03 | 3 | Supabase를 활용해 공유 업무 데이터의 SSOT를 유지한다 | 테이블·필드별 원본과 쓰기 주체 목록 필요 |
| R04 | 4 | 작가가 배송 일정을 지킬 수 있는 판매 가능 수량을 직접 정하며 플랫폼은 생산 역량에 따른 일률적 상한을 두지 않는다. 물류센터 실물 재고와 분리한다 | 의미 확정. 주문 차감·취소 복원·수정 방식 및 코드 검증 필요 |
| R05 | 5 | 환불·취소가 물류센터 실물 재고를 자동 변경해서는 안 된다. 반품이 필요한 물건은 해당 작가의 등록 주소로 보낸다 | 출고 전 취소·주소 확정·복수 작가 반품 시나리오 정의 필요 |

## 3. 데이터 원본과 변경 책임

SSOT는 같은 데이터를 양쪽 화면이 각자 수정하거나, 모든 외부 시스템의 사실을 Supabase가 임의로 결정한다는 의미가 아니다. **데이터마다 기준 원본과 변경 주체를 하나로 정하고**, 다른 시스템의 표현은 동기화한다.

다음은 구현 전 검토할 소유권 초안이다. Supabase의 구체적인 테이블명과 기존 트리거·RPC·웹훅을 조사한 뒤 확정한다.

| 데이터 | 기준 원본 / 변경 주체 제안 | 다른 시스템의 역할 |
| --- | --- | --- |
| 작가 프로필·상품 업무 정보·정산가 버전 | Supabase / 권한이 있는 작가·운영 API | Shopify와 프론트는 필요한 정보만 반영 |
| 결제·환불 거래 사실 | Shopify 및 연결 결제 시스템의 확정 거래 | Supabase에 외부 ID·상태·시각을 보존하고 대조 |
| 주문별 정산 근거·조정 내역 | Supabase / 검증된 정산 처리 | 대시보드는 같은 근거를 조회 |
| 작가 판매 가능 수량 | 작가가 납기 준수 역량에 따라 직접 설정 / 주문에 따른 변경은 단일 처리 경로 | 물류센터 보유량으로 설정 상한을 정하거나 물류 실물 수량을 덮어쓰지 않음 |

| 구매 화면의 판매 가능 수량 | 작가 설정과 확정된 주문 차감·예약 규칙을 반영하는 단일 계산 경로 | Shopify와 프론트에 동기화; 물류 실물 수량을 별도 판매분으로 중복 합산하지 않음 |

외부 연동에는 중복 방지 키, 재시도, 처리 이력, 순서 역전 처리, 실패 목록, 주기적 대조가 필요하다. 웹훅만으로 모든 이벤트가 한 번씩 순서대로 처리된다고 가정하지 않는다. Shopify도 중복 웹훅 전달을 처리하도록 안내한다. [공식 웹훅 문서](https://shopify.dev/docs/apps/build/webhooks)

## 4. 재고·취소·반품 원칙

### 4.1 작가 판매 가능 수량과 물류 실물 재고

**확정 사항:** 작가 대시보드의 재고는 작가가 배송 일정을 지켜 판매할 수 있다고 판단한 수량이다. 완제품 보유량만을 의미하지 않으며, 제작 역량에 따른 판매분도 포함할 수 있다. 플랫폼이 작가의 역량을 일률적으로 판단해 사업상 설정 상한을 두지 않는다.

| 구분 | 의미 | 관리 원칙 |
| --- | --- | --- |
| 작가 판매 가능 수량 | 작가가 배송 일정을 지킬 수 있다고 판단해 설정한 판매량 | 작가가 직접 결정; 물류 실물 재고로 상한을 제한하지 않음 |
| 물류센터 실물 수량 | 실제 도착한 작품을 확인해 기록한 수량 | 실제 입고·출고·검수·조정 사실로 관리 |
| 주문별 처리 수량 | 주문 상품별 주문·입고·출고·취소·반품 수량 | 작가와 상품·수량을 연결해 부분 처리를 추적하는 설계 필요 |

플랫폼의 일률적 설정 상한이 없다는 결정은 작가가 설정한 판매량을 넘겨 계속 주문을 받는 무제한 판매를 의미하지 않는다. 작가 설정값을 판매에 반영하되, 주문 차감 시점·예약 방식·취소 후 판매량 복원·수량 재설정 규칙은 다음 설계에서 확정한다. 입력값 유효성 검증은 생산 역량에 대한 사업상 상한과 구분한다.

**설계 제안:** 작가가 수량을 수정해도 이미 수락한 주문의 이행 의무는 별도 보존한다. 물류 입고·출고만으로 판매 가능 수량을 다시 차감하거나 증가시키지 않아 중복 반영을 방지한다. 판매 가능 수량이 남아 있더라도 입고되지 않은 작품은 물류센터에서 출고할 수 없다.

작가 → 물류센터 이동 중, 물류센터 → 구매자 배송 중, 구매자 → 작가 반품 중 상태는 물리적 이동 기록으로 추적한다. 작가 수령 후 검수·재판매 가능 여부가 판매량 설정에 미치는 영향은 별도 결정한다. 마지막 판매 가능 수량의 동시 구매와 세트 구성품 공유도 검증한다.

### 4.2 사건별로 허용되는 변화

| 사건 | 물류센터 실물 수량 | 별도로 처리할 사항 |
| --- | --- | --- |
| 출고 전 주문 취소 | 취소 이벤트만으로 증가·감소시키지 않음 | 예약 해제와 출고 중단의 허용 범위 결정 필요 |
| 출고 후 환불 승인 | 환불 이벤트만으로 증가시키지 않음 | 결제 환불·정산 조정·반품 필요 여부를 분리 |
| 구매자가 작가에게 반품 발송 | 물류센터 재입고로 처리하지 않음 | 상품별 작가·수량·반품 주소·송장을 기록 |
| 작가가 반품 수령 | 물류센터 수량 변경 없음 | 검수 결과에 따른 작가 재고 반영 시점 결정 |
| 실제 물류 입고·출고·재고 조정 | 물류에서 확인한 사건으로만 변경 | 중복 반영 방지 및 조정 사유·행위자 기록 |

**미결정:** 사용자의 “물류 재고에 관여하지 않음”에 예약 해제도 포함되는지 확인한다. 실물 수량과 예약 수량을 구분하지 않으면 출고 전 취소 후에도 재고가 계속 묶이거나 잘못 출고될 수 있다.

반품 주소는 해당 작가의 등록 주소를 사용한다. 권장안은 반품 승인 시 유효한 주소를 반품 건에 저장하고, 라벨 발급 이후 주소 변경은 별도 정정 절차로 처리하는 것이다. 구매 시점 주소와 반품 시점 주소 중 어떤 것을 사용할지는 확정이 필요하다.

복수 작가 주문의 반품 분리, 일부 수량 반품, 교환·재배송, 파손·분실, 반품 없는 환불, 반품 배송비 부담, 수령 거절, 장기 미수령도 정책을 정한다. 취소·환불이 항상 물건 이동을 동반하는 것은 아니다.

### 4.3 작가별 입고·합포장·선출고

**2026-09-27 사용자 운영 방향 확정(D018):** 기본 업무 흐름과 역할을 먼저 설계하고, 예외는 해당 단계에 추가한다. 역할별 화면 구성과 정상 사례는 [작가·물류 기본 설계](../../../blank-seoul-admin/doc/logistics/ARTIST_LOGISTICS_WORKFLOW.md)를 따른다. 해당 문서는 설계안이며 구현·검증 완료의 증거가 아니다.

- 작가: 주문 확인 → 제작 → 물류센터로 발송 → 해당 주문 상품의 발송 완료 기록.
- 물류 작업자: 입고 예정 확인 → 실제 상품의 바코드 스캔·수량 확인 → 입고 작업 완료 → 우체국 일괄 접수 → 포장·실제 출고.
- 시스템: 발송 완료한 주문 상품을 입고 예정으로 연결하고, 실제 입고분의 주문 연결·준비 여부·합포장 대상을 계산한다. 정상 건마다 작업자가 주문을 찾아 배정하거나 합포장 조합을 고르는 방식은 기본안으로 삼지 않는다.
- 작가의 입력 오류 가능성을 고려한다. 발송 완료를 실제 도착으로 간주하지 않으며 국내 운송장번호를 필수 연결 기준으로 삼지 않는다.
- 한 주문에 A·B·C가 있을 때 A·B의 상품·수량이 모두 준비되면 A+B 합포장, C는 대기한다. 한 작가의 일부 상품·수량만 먼저 보내지 않는다.
- 주문번호로 작가별 상품의 입고·접수·출고 진행과 배송 묶음을 조회한다. 입고 작업 완료가 미도착 상품까지 입고 완료시킨다는 뜻은 아니다.

**설계 제안(D019):** 기존 입고 연결은 보존하고 새로 확인한 수량만 남은 주문에 연결한다. 접수 시작 시 배송 구성을 고정하고, 이후 추가 입고는 별도로 처리한다. 접수와 실제 출고를 구분하여 실제 출고 시 실물 수량을 차감한다. 재고가 창고에 남아 있다는 이유로 이미 연결한 상품을 다른 주문에 중복 배정하지 않는다. 수량 기록·접수 보호·재시도 등 내부 구현 방식은 후속 상세 설계 대상이다.

**미결정:** 동일 상품의 복수 주문에 대한 배정 우선순위와 주문 간 대체 가능 범위, 맞춤 상품 식별, 스캔 중 저장·실물 재고 반영의 정확한 시점, 추가 배송비·납기·정정 정책. 같은 작가의 부분 선출고 허용 여부는 더 이상 미결정이 아니며 금지로 확정됐다. 고객 안내·정산·반품 영향은 관련 모듈에서 함께 검토한다.

**유지하는 검토 조건:** 배송 건마다 상품·작가·수량·송장을 연결하고, 미입고·취소·이미 출고된 수량을 다시 출고하지 않는다. 일부 배송으로 주문 전체를 완료 처리하지 않는다. 실제 무게·부피·파손 위험 등 포장 적합성을 확인하고, 고객별 남은 상품 표시와 작가별 정산·환불·반품을 함께 검토한다.

**구현 근거의 한계:** 2026-09-24의 [물류 검토 및 재현 결과](2026-09-24-fulfillment-review.md)는 당시 코드 증거다. 2026-09-27 로컬 읽기에서는 기존 발송·스캔·접수 화면의 연결을 확인했다. 새로운 일부 작가 합포장·입고 작업 완료 기준을 구현하거나 운영 DB·실제 배송을 검증한 것은 아니다.

## 5. 구매 시점 정산가 스냅샷

정확한 용어는 **스냅샷(snapshot)**이다. 주문 상품마다 구매 당시의 정산 조건을 고정해 저장한다. 이후 작가가 상품의 현재 정산가를 바꿔도 이전 주문의 근거는 바뀌지 않는다.

예: 정산 단가 30,000원일 때 2개 구매 → 기본 정산 근거는 60,000원. 나중에 단가를 35,000원으로 변경해도 이전 주문을 70,000원으로 다시 계산하지 않는다. 세금·수수료·차감의 별도 규칙은 추가 결정한다.

### 필수 설계 조건

- “구매 시점”을 주문 생성 / 결제 승인 / 결제 완료 중 무엇으로 볼지 결정한다. 미결제·예약 결제·추가 결제도 포함한다.
- 정산가 변경은 이전 값을 삭제하지 않고 버전과 적용 시각을 보존한다.
- 주문 알림 수신 시점의 최신 가격을 복사하면 안 된다. 지연 도착한 주문도 구매 시점에 유효한 정산 조건을 조회할 수 있어야 한다.
- 주문 상품 단위로 주문·라인·작가·SKU 식별자, 수량, 정산 단가, 통화, 가격 버전, 기준 사건 시각과 기록 시각을 보존한다.
- 수수료·할인 부담·환율 등 실제 정산에 필요한 조건은 해당 적용 시점과 규칙 버전을 명시한다. 세무 판단 시점을 구매 시점과 무조건 동일하게 취급하지 않는다.
- 과거 버전을 찾지 못하면 정산 보류 및 확인 대상으로 보내고, 현재 단가로 조용히 대체하지 않는다.
- 취소·부분 환불·정산 후 환불은 원본을 덮어쓰지 않고 원거래에 연결된 조정 내역으로 남긴다.
- 금액은 통화별 최소 단위 정수 또는 고정 소수점으로 계산하고 반올림 규칙을 통일한다.
- 주문 수정·같은 SKU 추가 구매·중복 웹훅·재처리에도 중복 정산이나 단가 재선택이 없어야 한다.
- 주문 시점 조건 보존과 정산 확정·지급 결과 보존을 구분한다. 지급 완료 스냅샷만으로 구매 시점 단가 보존을 보장할 수 없다.

정산 주기, 정산 확정 조건, 할인 부담, 지급 후 환불 공제, 음수 잔액, 지급 실패 재시도, 계좌 변경 승인, 세금 처리 기준은 별도 정책 결정과 확인 대상으로 남긴다.

## 6. 동시 이용과 성능 목표

사용자 요구는 **작가 10,000명 + 방문자·구매자 10,000명 동시 이용**이다. 등록 사용자 수나 월간 방문자 수로 대체하지 않는다. 동시에 접속한 사용자 수와 동시에 실행되는 DB 쿼리 수는 다르므로 행동 빈도와 서버 요청 수를 모델링한다.

예를 들어 20,000명이 평균 10초마다 동작하면 초당 2,000개 사용자 동작이다. 한 동작의 API 호출 개수, 캐시 적중률, 쓰기 비율에 따라 실제 서버·DB 부하는 달라진다. 이 수치는 설명용이며 확정된 부하 조건이 아니다.

### 측정 가능한 목표 초안 — 아직 합의·달성하지 않음

| 항목 | 제안 기준 | 측정 조건 |
| --- | --- | --- |
| 핵심 읽기 API | p95 500ms 이하, p99 1.5초 이하 | 캐시 적중·미적중 분리, 대상 리전 명시 |
| 일반 저장 API | p95 1초 이하 | 외부 처리 완료를 기다리는 작업은 접수 시간과 완료 시간을 구분 |
| 예상치 못한 실패 | 핵심 API 5xx·타임아웃 비율 0.1% 미만 | 의도된 입력 거부는 분리; 과부하 429·구매 실패는 별도 집계 |
| 정합성 | 시험에서 중복 정산·재고 중복 차감·작가 간 데이터 노출 0건 | 재전송·동시 수정·장애 주입 후 대조 포함 |
| 월간 가용성 | 99.9% 이상을 논의 출발점으로 제안 | 핵심 경로·외부 장애 포함 범위·측정 위치 정의 필요 |
| 동기화 지연 | p95·최대 지연과 실패 큐 길이 추적 | 주문·재고·일반 콘텐츠마다 허용 지연을 따로 결정 |

숫자는 설계 논의를 위한 후보이며 성능 보증이 아니다. 운영 리전, 모바일 네트워크, 상품·주문 누적량, 작가별 데이터 편차, 호스팅·DB 사양 및 예산을 먼저 기록한다.

### 검증 단계

1. 실제 사용 흐름과 데이터 규모를 정한다: 탐색·검색·장바구니·구매·작가 조회·상품 저장·정산 조회 비율.
2. 익명화한 대표 데이터와 독립된 시험 환경을 준비한다. 실제 결제·운영 이메일·물류 출고를 발생시키지 않도록 연동 시험 환경을 사용한다.
3. 낮은 부하에서 기준치를 측정한 뒤 합계 1,000 → 5,000 → 20,000 동시 세션으로 단계적으로 증가시킨다.
4. 예시 시험안: 최대 목표 부하 60분 유지, 일반 부하 수 시간 유지, 드롭 직후 급증, 캐시 초기화, 월말 정산과 주문 동시 처리. 시간·요청 비율은 시험 전에 확정한다.
5. 응답 시간 외에 처리량, 오류·재시도, DB 연결·락·IO, 큐 적체, 데이터 정합성, 비용을 함께 평가한다.
6. 실패하면 확인된 수용량·병목·개선·재시험 결과를 기록한다. 단위 테스트·빌드 성공만으로 20,000명 지원 완료를 선언하지 않는다.

외부 API 속도 제한과 Shopify 체크아웃 수용량도 실제 계약·허용 시험 범위에 맞춰 확인한다. 캐시는 작가별 비공개 정보가 섞이지 않도록 범위를 나누고, 최종 재고·정산 판단에는 오래된 캐시를 사용하지 않는다.

## 7. Supabase Disk IO 경고 대응

현재 확인된 증거는 사용자가 전달한 `Disk IO budget is being consumed on shopify-database` 경고다. 운영 대시보드·쿼리 통계를 직접 확인하지 않았으므로 원인은 아직 미확정이다.

Disk IO 예산은 저장 용량 잔여량과 별개다. Supabase 문서는 일부 컴퓨트 크기의 디스크 IO 버스트 예산이 소진되면 기본 처리 성능으로 돌아간다고 설명한다. 실제 수요가 기본 처리량보다 높으면 지연이나 타임아웃이 발생할 수 있으므로, 목표는 지속 부하가 가용 처리량 안에 있도록 만드는 것이다. [Compute and Disk](https://supabase.com/docs/guides/platform/compute-and-disk)

확인할 항목:

- 경고 발생 시각과 당시 트래픽·배치·정산·동기화·백업 작업의 시간대.
- 현재 컴퓨트·메모리·디스크 구성, IO 예산 추이, IOPS·처리량·지연·DB 연결 수.
- 호출이 잦거나 느린 쿼리, 전체 테이블 스캔, 대량 정렬·임시 파일, 잦은 업데이트, 큰 응답.
- 폴링 간격, 중복 구독, 요청마다 전체 집계, N+1 조회, 과도한 로그·재시도.
- 인덱스·RLS 조건·페이지네이션·집계 방식, WAL·테이블 증가, 유지보수 작업의 영향.

개선은 원인을 확인한 뒤 쿼리·데이터 접근 최적화, 캐시·집계·큐 처리, 배치 동시성 제한, 필요한 용량 증설 순으로 비교한다. 인덱스도 쓰기 비용이 있으므로 무조건 추가하지 않는다. 지속 처리량이 부족하면 코드 개선만으로 해결된다고 약속하지 않는다.

경고 임계값과 담당자 알림, 비핵심 배치 일시 중단, 처리 속도 제한, 복구 후 누락 대조를 운영 절차에 포함한다. 지표상 여유와 장시간 부하 시험이 확인되어야 완료로 판정한다. [High Disk I/O 대응 문서](https://supabase.com/docs/guides/troubleshooting/exhaust-disk-io)

## 8. 두 프로젝트를 함께 다루는 agent-bridge

요구: 한 작업의 필요에 따라 storefront와 admin을 함께 읽고 수정하고 검증할 수 있어야 한다. Supabase SQL 실행·마이그레이션 적용·Git push는 사용자가 직접 한다.

현재 storefront의 `.agent-bridge/pipeline.config.json`은 `workspaceRoot: "."`이고, `SAFETY.md`는 storefront 한 폴더만 허용한다. **두 프로젝트 자동 수정은 아직 이 문서 작성으로 활성화되지 않는다.**

후속 구현 요구사항:

1. 두 저장소를 명시적으로 등록한다. Downloads 전체가 아니라 storefront와 admin의 정확한 루트를 허용한다.
2. 실행기 설정, Codex/Gemini의 실제 권한, 테스트 샌드박스, diff 수집 경로가 모두 두 루트를 지원하는지 검증한다. JSON에 경로만 추가해서 완료로 보지 않는다.
3. 작업별로 각 저장소의 시작 커밋·기존 변경·허용 파일 범위를 기록하고 기존 사용자 변경을 보존한다.
4. 동시 실행이 같은 저장소·파일을 수정하지 않도록 잠금 또는 작업별 격리 환경을 설계한다.
5. 공유 DB·API 계약 변경은 양쪽 영향을 검토하고, 호환되는 배포 순서와 되돌리는 절차를 적는다.
6. 변경된 각 프로젝트의 적절한 검증과 필요한 연동 계약 검증을 실행한다. 성공·실패·미실행을 구분한다.
7. `REPORT.md`에 저장소별 diff·테스트·수동 작업을 기록하고, `REVIEW.md`에는 실제 변경과 실행 증거에 근거한 판정을 남긴다.
8. SQL 파일 작성·검토는 가능하지만 운영 SQL 적용·Git push를 자동 실행하지 않는다. 완료 보고에는 사용자가 적용해야 할 항목을 분리한다.

이 문서는 장기 기준이고 `.agent-bridge/COMMAND.md`는 한 번의 실행 지시다. 단일 작업 지시가 장기 기준을 덮어쓰지 않도록 요구사항 ID와 문서 버전을 참조한다.

연결 범위·요청량·요금제 검토는 [문의 알림 검토](INQUIRY_DELIVERY.md)에 둔다. 사용자 확인상 Vercel과 Supabase는 무료 사용 중이다. Broadcast 채택·게스트 실시간 인증·응답 시간과 비용 목표는 아직 설계 제안이며 구현 완료 또는 유료 전환 승인을 뜻하지 않는다.

## 10. 실행 순서와 완료 증거

우선순위는 현재 제안이다. 운영 장애가 진행 중이면 IO 진단과 피해 제한을 먼저 한다.

분석 진행 방식은 [전체 플랫폼 분석·검증 계획](PLATFORM_ANALYSIS_PLAN.md)을 따른다. 두 프로젝트와 Supabase·Vercel·Shopify·물류 연동의 기능·데이터 책임을 먼저 목록화하고, 핵심 업무 흐름을 요구사항과 대조한다. 미결정 정책이 있어도 독립적인 현황 분석을 진행한다. 논리적인 모듈 구분과 실제 코드 재구성은 별도 판단하며, 전체 분석 결과가 나오기 전 대규모 구조 변경을 전제하지 않는다.

### 핵심 인수 시나리오

- R04/R05: 환불·취소·부분 반품·중복 이벤트 후 물류 실물 수량이 임의 복원되지 않는다.
- R04: 실제 입고·출고는 한 번만 반영되고 작가·물류 간 이동 수량이 대조된다.
- R04: 작가 판매 가능 수량을 물류센터 실물 보유량으로 제한하지 않고, 작가 수량 설정과 기존 주문의 처리를 구분한다.
- R12: A/B 작가 전체 입고 시 합포장, A만 입고 시 선출고, B 후속 입고 시 잔여 출고를 처리하고 상품·수량·송장이 정확히 연결된다.
- R12: 중복 입고 알림·동시 출고 요청에도 중복 출고가 없으며, 부분 출고를 주문 전체 출고 완료로 표시하지 않는다.
- R12: A 송장 발급 후 B 입고에도 A 묶음과 송장이 유지되고, 서로 다른 작가의 배송 식별자가 충돌하지 않는다.
- R12: 외부 출고 성공 후 로컬 저장 실패를 재시도하면 남은 상태 갱신이 완료된다. 2개 주문을 1개씩 입고해도 누적 수량이 정확하다.
- R05: 복수 작가 주문의 반품지가 상품별로 정확하며 라벨 발급 후 주소 변경이 추적된다.
- R06: 가격 변경 전 주문·변경 후 주문·지연 웹훅·주문 수정에서 각각 올바른 정산 버전을 사용한다.
- R06/A04: 부분 환불·정산 완료 후 환불·작가 탈퇴 후 정정이 원거래를 보존하고 중복 공제·지급을 만들지 않는다.
- R03/A01: 다른 작가 ID를 요청에 넣어도 비공개 데이터 접근이 차단된다.
- R07/R09/R10: 합의된 최대 부하와 장시간 부하에서 응답·오류·정합성·IO·비용 기준을 만족한다.
- R08: 두 프로젝트가 함께 변경되고 한쪽 검증 실패 시 전체 작업을 성공으로 보고하지 않는다.

## 12. 대화·문서 업데이트 규칙

1. 사용자는 생각·사례·불편한 점을 자유롭게 전달한다.
2. 작성자는 관련 요구사항에 연결하고 **확정 / 제안 / 미결정 / 검증 완료**를 구분한다. 답이 없는 질문을 합의로 간주하지 않는다.
3. 운영 판단에 영향을 주는 질문은 한 번에 핵심 한 가지부터 논의한다.
   다만 질문은 먼저 전체 기능과 업무 흐름을 조사해 묶는다. 임의의 개별 사례 질문만으로 분석을 진행하지 않고, 확인된 현재 동작과 선택의 영향을 근거로 논의한다.
4. 결정되면 아래 기록과 관련 본문을 함께 수정한다. 바뀐 이유와 기존 결정의 대체 여부도 남긴다.
5. 구현 지시는 요구사항 ID·대상 저장소·완료 조건·검증·수동 적용 항목을 포함한다.
6. 완료 판정에는 변경 경로, 테스트 명령·결과, 실행 ID 또는 보고서 링크, 확인하지 못한 범위를 기록한다. 테스트 보고만으로 사업 정책을 새로 확정하지 않는다.
7. 새 발견으로 범위가 커지면 우선순위와 완료 조건을 갱신한다. 과거 보고서를 현재 구현 보증으로 사용하지 않는다.
8. 작업 시작 시 [공통 목차의 현재 초점·문서 참조 규칙](README.md)을 확인한다. 과거 전략, 코드에 남아 있는 기능, 이전 COMMAND를 현재 목표나 새 작업 권한으로 해석하지 않는다. 확정 방향을 다시 질문하는 대신 변경이 필요한 구체적 근거를 제시한다.

### 다음에 결정할 질문

질문은 전체 목표·출시 범위·사용자 여정부터 묶어 논의한다. 아래 번호는 구현 우선순위가 아니며, 물류 질문부터 차례대로 답해야 하는 목록도 아니다. 기능별 질문은 모듈 분석에서 확인한 현재 동작과 선택의 영향을 함께 제시한다.

현재 질문 목록은 [사용자 여정 Q01–Q12](USER_JOURNEYS.md)에 상세화했다. Q01은 한국 제조 상품 우선·K-Food 보류까지 확정됐다. 남은 우선 상품군·판매 시장·고객 가치·한국 제조 확인 기준을 논의한 뒤, Q02 입점 활성화와 상품 심사, Q03 공개 프로필·계정 종료, Q04 벤더 발주 포함 여부로 이어가는 순서를 제안한다. 아래 최초 질문도 해당 Q 항목에 포함한다.

1. 입고 작업 완료 후 준비된 작가를 묶어 물류 작업자가 일괄 접수하는 방향은 D018로 정리됐다. 남은 질문은 동일 상품의 주문 배정 순서·맞춤품 식별·대기 알림이다.
2. 같은 작가 일부 수량 선출고는 금지(D018). 작가별 분리 배송에 따른 추가 배송비 부담과 고객 안내는 어떻게 하는가?
3. 작가가 약속하는 배송 일정의 기준은 무엇이며, 판매 가능 수량의 차감·재설정·취소 복원은 어떻게 하는가?
4. 정산가를 고정하는 구매 시점은 주문 생성인가, 결제 완료인가?
5. 출고 전 취소 시 예약 해제·출고 중단까지 자동화해도 되는가?
6. 반품 주소는 언제 확정하며 반품 배송비·검수·재판매 처리는 누가 책임지는가?
7. 초기 판매 방식·시장·출시 범위와 단계별 운영 예산은 무엇인가?
