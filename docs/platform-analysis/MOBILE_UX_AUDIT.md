# 모바일 구매·문의 UX 검토 및 개선

검토: 2026-10-03~04 · 후속 구현: 2026-10-04 · 대상: Storefront 작업 트리(기준 HEAD `1f152f6` + 기존 미커밋 변경)

연결: R01/R11, M04 구매 경험, M10 고객지원, 구매·문의 여정. [공통 목표](PROJECT_DIRECTION.md)와 한국 제조·한국 출고 원칙을 따른다. 이번 검토는 전체 플랫폼·대규모 부하 시험의 완료 판정이 아니다.

## 1. 결론과 적절성 판단

기본 반응형 배치는 갖췄지만, 최초 점검에서 실제 구매 버튼 가림과 문의 전환 문제가 발견됐다. 사용자가 지적한 작은 화면의 담기 버튼, 메시지 전송 과정, 이전 문의 복귀는 구매자 신뢰와 운영 문의 감소에 직접 연결되므로 개선 우선순위가 높다.

| 항목 | 판단 | 이번 반영 |
| --- | --- | --- |
| 담기 버튼 안에 가격 반복 | 본문에 선택 옵션 가격이 표시되므로 필수 아님. 좁은 공간에서 긴 문구가 행동을 가림 | 본문 CTA를 `Add to Cart`로 단축. 모바일 수량·찜 아래 전체 폭, 최소 56px 높이. 위의 상품 가격 및 별도 스티키 영역 가격은 유지 |
| 전송 중 안내 | 버튼만 비활성화하면 메시지 접수 여부가 불분명 | 전송 중 말풍선·Sending 표시, 응답 확인 후 Sent, 실패 시 초안 복원과 오류 표시 |
| 첫 메시지 후 대화방 이동 | 생성 응답의 첫 메시지를 토큰 변경 effect가 지워 다시 조회하던 문제 | 생성 응답의 메시지·상품 맥락을 초기 대화에 보존. 느린 재조회에도 빈 기록 화면으로 되돌아가지 않음 |
| 문의 목록 | 여러 상품·배송·반품 문의를 찾는 데 필요 | `Your inquiries` → 선택/새 문의, 브라우저 저장 및 새로고침 복원. 계정 전체·다른 기기 목록과는 구분 |
| 장바구니 고정 CTA | 하단 메뉴가 클릭 영역을 덮는 구매 방해 결함 | `/cart`에서 전역 하단 메뉴를 숨기고 CTA를 `Checkout` / `Continue to checkout`으로 정리 |
| 검색 | 기존 동작은 카테고리 스크롤 또는 전체 목록 이동으로, 입력 단어 검색을 충족하지 못함 | `/search?q=`에서 Shopify 상품 검색, 관련도 결과·빈 결과·조회 오류·재시도·24개 단위 다음 페이지 |
| 상품 이미지 | 마우스 hover 확대만으로 모바일 상세 확인이 부족 | 터치/키보드로 이미지 뷰어, 확대/축소·확대 이미지 스크롤, 여러 이미지일 때 이전/다음 |
| 모달 창 | 옵션창 z40보다 헤더 z50이 높아 배경 조작 가능, 메뉴 초점이 배경에 남음 | 공통 native `dialog.showModal()`로 메뉴·옵션·장바구니·이미지 창의 초점/배경 차단/Escape/초점 복귀 처리 |
| 제작 슬롯 문구 | 판매 가능 수량으로 수작업·주문 제작 여부를 추정할 수 없음 | 담기 영역의 `crafting slots` / `Made to Order`를 판매 가능 여부·수량으로 교체 |

이 선택은 특정 사이트의 외형을 그대로 적용한 것이 아니다. 구매 CTA와 가격의 구분은 상품 페이지에서 가격·구매 행동을 명확히 하라는 [Baymard의 구매 흐름 점검](https://baymard.com/blog/ecommerce-ux-audit)을 참고한 현재 화면의 설계 판단이다. 전송 피드백은 [NN/g의 처리 상태 안내 원칙](https://www.nngroup.com/articles/designing-for-waits-and-interruptions/)을 적용했다. 가격을 모든 CTA에서 제거해야 한다는 보편 규칙으로 해석하지 않는다.

## 2. 최초 점검 근거

Chrome 터치 에뮬레이션에서 11개 경로 × 5개 화면 = 55개 초기 상태를 점검했다.

- 화면: 320×568, 390×844, 430×932, 768×1024, 844×390.
- 경로: 홈 preview/live, 전체 상품, 카테고리, 상품 상세, 빈 장바구니, 찜, 작가, 로그인, 주문 조회, 반품 정책.
- 가로 문서 넘침 0건, pageerror 0건. 50개 HTTP 200, 로컬 `/collections/jewelry-charms` 5개 HTTP 404.
- 같은 카테고리의 공개 운영 URL은 HTTP 200이었다. 로컬 카탈로그 차이이며 운영 카테고리 장애로 판정하지 않았다.
- 390px 상품을 담은 장바구니의 고정 CTA는 y779.16~830, 하단 메뉴는 y779~844. CTA 중앙 hit test 결과가 계정 메뉴 `You`였다.
- 메뉴 Escape 닫기는 기존에도 동작했지만 열 때 초점 이동/모달 의미가 부족했다. 옵션창 위에 헤더가 남아 있었다.
- 초기 모바일 입력 글꼴은 확인한 필드에서 16px. 페이지 확대 허용과 기본 safe-area 대응은 존재했다.
- 일부 헤더·찜 버튼은 28~38px였다. 개선 후보이며 모두 WCAG 실패로 분류하지 않는다. [WCAG 2.2 AA의 24px 최소 기준과 간격 예외](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)와 44px 조작 편의 목표를 구분한다.

초기 상태 점검이 로그인·결제·실물 키보드·모든 옵션 조합 검증을 뜻하지 않는다.

## 3. 문의 목록의 현재 범위

원본: [ConciergeChat](../../app/components/ConciergeChat.tsx), [브라우저 기록 처리](../../lib/inquiries/history.ts).

- 기존 최근 문의 토큰 하나를 기록으로 이관하고 새 문의의 접근 토큰·제목·활동 시각·마지막 확인 상태를 저장한다.
- 상품 문의는 상품 제목, 일반 문의는 첫 메시지 앞부분을 제목으로 사용한다. 이메일·대화 전문은 목록에 추가 저장하지 않는다.
- 대화 선택 시 기존 토큰 API로 권한을 검사한다. 토큰을 아는 브라우저가 그 대화에 접근하는 기존 계약을 유지한다.
- 존재하지 않거나 만료된 대화의 404/410 응답은 기록에서 제거한다. 조회 장애는 빈 대화 성공으로 표시하지 않고 재시도를 제공한다.
- 읽지 않은 답변·진행 상태는 마지막으로 확인한 정보다. 목록에서 모든 문의를 동시에 폴링하지 않으며, 선택한 대화를 열 때 최신 내용을 확인한다. 목록 열람만으로 메시지를 읽음 처리하지 않는다.
- 작성 중 초안은 대화 전환 시 세션 메모리에서 보존한다. 새로고침 후 미전송 초안 복원은 제공하지 않는다.
- 브라우저 저장을 지우면 목록도 사라진다. 기존에 최근 토큰 교체로 잃은 문의를 이 변경만으로 되살리지는 못한다. 보관한 접근 링크로 열면 목록에 다시 등록된다.

**후속 기능:** 계정에 연결된 전체 문의·기기 간 복원, 비회원 이메일 소유 확인 후 복구, 서버에서 권한을 확인한 목록의 페이지 조회. 이메일 문자열 일치만으로 문의를 공개하지 않는다. 이 기능은 아직 구현하지 않았으며 현재 화면은 `Saved on this browser`로 범위를 알린다.

## 4. 구현 경계

- [AddToCartSection](../../app/components/AddToCartSection.tsx): 구매 영역 배치·문구. 가격 데이터·장바구니 저장·판매량 계약 변경 없음.
- [Modal](../../app/components/Modal.tsx): native 모달의 초점/배경 inert 처리 및 중첩 시 스크롤 잠금 수명 관리. [HTML dialog 동작](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog)을 따른다.
- [MobileStickyBottomBar](../../app/components/MobileStickyBottomBar.tsx): 숨은 버튼의 키보드 접근 차단. 화면을 한 번에 아래로 이동해 구매 영역을 건너뛰는 경우에도 스티키 상태가 맞도록 프레임당 한 번 위치 확인.
- [검색 화면](../../app/search/page.tsx), [로딩 화면](../../app/search/loading.tsx), [Shopify API](../../lib/shopify/api.ts): 상품 전체를 브라우저로 내려받아 검색하지 않고 [Storefront search](https://shopify.dev/docs/api/storefront/latest/queries/search)와 커서를 사용. 검색어 200자, 페이지 24개. 검색 결과는 noindex.
- 문의 API의 저장/중복 방지/번역/알림/권한 로직과 SQL은 변경하지 않는다. 전송 성공은 서버 응답으로 확인하며 운영자 답변이나 읽음을 뜻하지 않는다.
- 사용자가 직접 Supabase SQL 적용·Git push를 수행한다는 운영 방침 유지. 이번 변경에는 신규 SQL이 없다.

## 5. 후속 검증 결과

모든 채팅 생성·재시도 시험은 가짜 API 응답으로 수행했으며 실제 문의·메일은 보내지 않았다. 검색은 로컬 서버를 통한 실제 공개 상품 읽기를 확인했다.

| 확인 | 결과 |
| --- | --- |
| 본문 담기 버튼 320/334/390/430/768/1024/1440px | 7개 폭 모두 문구 한 줄·높이 56px·문서 가로 넘침 없음. 실제 로컬 장바구니 추가 확인 |
| 모바일/데스크톱 전송 | 1.2초 지연 POST 중 말풍선, 성공 후 2.2초 지연 기록 조회에도 첫 메시지 보존, 중복 말풍선 없음 |
| 실패/재시도 | 초안 복원, 동일 requestId 재시도, 별도 문의 실패 후 원래 대화 복귀 |
| 키보드 | PC Enter 전송/Shift+Enter 줄바꿈, touch Enter 줄바꿈, IME/229/repeat 보호, 비회원 필수 입력 유지 |
| 문의 기록 390/1440px | 서로 다른 두 문의 생성·전환·이전 초안 보존·새로고침 복원·조회 실패 재시도. 목록에서 전체 문의 조회 fan-out 없음 |
| 갤러리/모달/결제 CTA 320/390/430/768px | 터치 확대·이미지 스크롤, 초점 내부 유지·Escape 닫기, 옵션창 배경 헤더 차단, 결제 버튼 중앙 직접 클릭 가능 |

[정리된 브라우저 근거](MOBILE_UX_EVIDENCE.json)에 초기 점검과 후속 확인을 분리했다. 개발 중 낡은 선택자/옛 검색 목적지를 기대한 시험 실패는 테스트를 갱신했으며, 태블릿에서 영역을 건너뛰는 스크롤의 스티키 미표시는 코드 보완 후 재검증했다.

## 6. 모바일 성능 표본과 남은 작업

공개 운영 홈(당시 preview 화면)을 새로운 Chrome 세션에서 읽기 전용으로 1회씩 측정했다. 로컬 변경의 배포 후 성능 측정이 아니다.

| 조건 | LCP | CLS | 받은 데이터 |
| --- | ---: | ---: | ---: |
| 일반 네트워크 | 1.97초 | 0 | 약 1.56MiB |
| 지연 150ms, 다운로드 1.6Mbps, 업로드 0.75Mbps, CPU 4배 제한 | 3.54초 | 0.044 | 약 1.56MiB |

제한 환경 LCP는 개선 후보지만 단일 실험 표본이다. [Core Web Vitals](https://web.dev/articles/vitals)의 실제 사용자 75백분위 평가나 전체 사이트 합격/실패로 해석하지 않는다. INP는 측정하지 않았다.

남은 확인 순서:

1. 사용자 배포 후 iPhone Safari·Android Chrome에서 키보드 개폐, 긴 메시지, 한글 조합, 이미지 확대, 장바구니 CTA, 목록 복원을 확인한다.
2. 문의 목록의 계정 연결/비회원 복구 계약을 정한 뒤 Admin 권한 검증과 함께 구현한다. 현재 브라우저 기록을 계정별 서버 기록이라고 표시하지 않는다.
3. 운영의 실제 LCP/INP/CLS와 이미지·JS 요청을 수집해 비용 대비 큰 성능 개선을 선택한다. 한 번의 측정만으로 카탈로그·정산·인프라 전체를 재설계하지 않는다.
4. 큰 카탈로그 검색 페이지네이션, 다양한 옵션·품절 상품, 로그인 상태, Shopify 결제/국가·배송비·결제 실패를 환경별로 검증한다. 실제 결제·운영 메시지 쓰기는 이번에 수행하지 않았다.
5. 28~38px 보조 조작 영역과 landscape 키보드 조합을 추가 실기 검토한다. 이번 55개 초기 상태 검사만으로 모든 터치·접근성 기준을 완료했다고 선언하지 않는다.

대규모 동시 이용, Supabase IO, 정산·물류의 전체 검증 상태는 기존 [검증 문서](VALIDATION.md)와 [모듈 지도](FEATURE_MAP.md)를 유지한다.
