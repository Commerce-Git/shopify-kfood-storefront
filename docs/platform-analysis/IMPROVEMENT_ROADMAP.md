# 목표 달성을 위한 개선 로드맵

2026-09-24 · 이번 작업은 분석과 계획까지다. 아래 개선을 이미 구현한 것으로 해석하지 않는다. 운영 사고가 확인되면 그 피해 제한이 우선이다.

## 0. 현재 우선할 일 — 목표 구체화와 전체 모듈 평가

아래 W00–W09는 1차 분석에서 도출한 개선 후보이며 즉시 실행할 확정 순서가 아니다. 개별 결함부터 수정하는 제안을 보정하여, 다음 분석 묶음을 먼저 진행한다.

**사업 범위 갱신(D015/D016):** 한국 제조 상품을 중심으로 작가의 판매·정산, 구매자의 신뢰, 지속 가능한 운영을 함께 추구한다. K-Food 전용 확장 작업은 보류 사업으로 분류한다. 공통 상품·물류·정산 기능은 현재 목표에 대한 기여로 평가하며, 기존 K-Food 관련 코드의 제거·중단 여부는 실제 사용/의존성을 확인한 후 별도 판단한다.

| 순서 | 수행 내용 | 완료 기준 |
| --- | --- | --- |
| 1 | 구매자·작가·운영자·물류 담당자의 목표와 전체 여정 정리 | 역할별 성공 시나리오, R/A 요구사항 연결, 출시 범위·정책·성능 수치의 확정/제안/미결정 구분 |
| 2 | M01–M12 전체 기능을 관리 가능한 단위로 상세화 | 각 기능에 주관 모듈·진입점·관련 저장소·데이터 책임·근거·미확인 지점 연결; 미분류 기능도 명시 |
| 3 | 모듈 사이의 계약과 운영 의존성 검토 | 입력/출력·상태 전이·쓰기 책임·권한·실패 복구 연결; 코드와 운영 적용 상태 분리 |
| 4 | 목표 대비 전체 차이와 구현 우선순위 제안 | 모든 모듈의 검토 상태, 빠진 기능·중복 규칙·결함·운영 미검증 사항을 함께 평가하여 작업 선택 |

단계별 결과는 기존 문서에 반영한다. 목표는 `PROJECT_DIRECTION`, 기능과 검토 범위는 `FEATURE_MAP`, 데이터 책임은 `DATA_AND_FLOWS`, 판정은 `REQUIREMENTS_MATRIX`를 원본으로 한다. 같은 사실을 여러 문서에 복사하지 않고 ID와 링크로 연결한다.

**구현 착수 기준:** 전체 모듈에 최소한의 현황·미확인 범위가 기록되고, 대상 변경의 목표·책임 경계·다른 모듈 영향·인수 기준이 설명되어야 한다. 모든 기능을 같은 깊이로 감사하거나 모든 운영 자료가 모일 때까지 기다릴 필요는 없다. 정책이 필요한 분기만 보류하고 독립적인 분석은 계속한다. 운영 사고 대응은 영향과 예외 사유를 기록하고 우선한다.

## 2. 권장 모듈 경계

- **주문 조건 모듈:** 주문 라인과 작가의 불변 ID, 구매 기준 시각, 가격 버전·정산 단가, 원본 이벤트를 보존한다.
- **판매량 모듈:** 작가 설정·예약/차감·취소 복원을 관리한다. 물류 실물 수량을 같은 필드로 갱신하지 않는다.
- **물류 원장 모듈:** 입고·검수·배정·출고·조정의 수량과 멱등 키를 한 책임으로 묶는다.
- **출고 모듈:** 확정된 묶음·라인/수량·송장·외부 결과·로컬 완료를 관리한다. 화면·cron·batch가 공통 검증을 사용한다.
- **정산 모듈:** 원거래 기반 정산·조정·마감·지급 결과·정정 이력을 관리한다. 화면의 금액 계산을 서버 규칙과 맞춘다.
- **이벤트 처리 모듈:** 수신·중복 방지·재시도·임대·실패 큐·대조를 담당하며 외부 호출 어댑터와 연결한다.

첫 구현은 기존 두 프로젝트에서 경계를 명확히 하는 방식으로 검토한다. 별도 서비스나 모노레포 전환은 필요성과 운영 비용이 입증된 후 선택한다.

Gemini의 구현 보고는 실제 변경 경로·명령·결과·남은 문제를 포함한다. 실행기는 가능한 검증을 직접 실행하고 Codex는 diff와 증거를 대조한다. 정책 변경은 보고서에서 임의 확정하지 않고 목표 문서에 기록한다.

## 4. 출시/확장의 완료 기준

1. 해당 출시 범위의 R번호와 정책이 확정되고, 관련 P1 결함이 해결되거나 기능 범위 조정이 사용자와 합의됐다.
2. 양쪽 앱·실제 DB·외부 연동의 배포 버전과 적용 상태가 일치한다.
3. 핵심 거래·물류·정산 흐름의 정상/부분/실패/재시도 시험이 통과한다.
4. API·DB·Storage의 역할 격리, 주문/재고/지급 대조, 경보·복구 담당과 절차를 확인한다.
5. 목표 부하와 장시간 시험에서 지연·오류·IO·정합성·비용 기준을 만족한다. 미검증 목표는 그대로 명시한다.

초기 출시 규모를 20,000명 목표보다 작게 정하려면 별도 합의와 실측 수용량을 기록한다. 테스트 몇 개 통과한 것을 규모 보증으로 바꾸지 않는다.

## 5. 업데이트 규칙

작업 완료마다 `FINDINGS`에 해결 상태·검증 ID를, `REQUIREMENTS_MATRIX`에 새로운 판정·범위를, `README`에 현재 다음 작업을 반영한다. 가격·반품·정산 정책 결정은 `PROJECT_DIRECTION` 원본에 남긴다. 과거 결과는 보존하고 해당 기준선에서 확인한 사실임을 유지한다.
