# 물류 입고 기준 합포장·작가별 선출고 검토

검토일: 2026-09-24 · 대상: `blank-seoul-admin` 로컬 작업 트리 · 연결 요구사항: R04/R12

공통 문서 목차: [플랫폼 분석 기준 문서](README.md)

## 결론

물류 포털에서 확인한 **주문 상품별 입고 상태**를 출고 후보 판단 기준으로 삼는 것이 현재 운영 방향과 일치한다. 어드민에는 이미 전체 입고 시 합포장, 작가별 전체 품목 입고 시 선출고 가능한 그룹을 만드는 로직이 있다.

권장 흐름은 `입고·검수 확인 → 아직 출고에 배정하지 않은 주문 품목으로 후보 생성 → 물류 작업자가 접수할 묶음 확정 → 송장 발급 → 패킹·출고`다. 입고 즉시 무조건 자동 출고하는 정책으로 확대하지 않는다. **송장이 발급된 묶음은 이후 입고 때문에 자동으로 바뀌지 않아야 한다.**

검토 당시 어드민에 기존 수정·미추적 SQL이 있었다. 그 변경을 포함한 로컬 코드를 읽었으며, 운영 배포 상태와 DB 마이그레이션 적용 여부는 확인하지 않았다. 어드민 코드 수정, SQL 실행, 실제 배송·Shopify 호출은 하지 않았다.

아래 경로·줄 번호는 검토 시점 기준이며 `blank-seoul-admin` 루트에 상대적이다.

## 1. 확인한 현재 동작

| 단계 | 코드 | 확인한 내용 |
| --- | --- | --- |
| 주문 품목 조회 | `app/api/3pl/orders/route.ts:32` | 창고별 `artist_orders` 중 취소되지 않은 품목을 조회 |
| 합포장 후보 계산 | `lib/3pl/orderGrouping.ts:129` | 미출고 작가가 2명 이상이고 활성 품목 모두 `received`이면 단일 그룹 생성 |
| 작가별 준비 판단 | `lib/3pl/orderGrouping.ts:273` | 그룹의 모든 품목이 `received`이면 `ready`; 일부 입고는 `pending` |
| 물류 작업자 접수 | `app/3pl/dashboard/components/FulfillmentTab.tsx:150` | 작업자가 선택한 `ready` 그룹을 확인 후 우체국 접수 |
| 실제 접수 대상 | `lib/3pl/epostService.ts:75` | 창고·주문·작가 조건으로 `received` 품목을 선택 |
| 패킹 완료 | `app/api/3pl/pack-complete/route.ts:86` | 입고 품목 조회 후 물류 재고 차감, Shopify 부분 출고, 로컬 상태 변경 |
| 물류 재고 분리 | `lib/supabase/stock.ts:126` | 창고 식별자를 포함한 `apply_warehouse_batch_stock_change` RPC 호출 |

현재 기본 그룹화는 **작가별 모든 주문 라인이 입고되었는지**를 본다. 같은 작가의 한 라인 수량 일부만 도착하는 경우까지 지원한다고 볼 수 없다.

## 2. 발견 사항

### F01 · 높음 · 송장 발급 후 추가 입고가 기존 출고 묶음을 바꾼다 — 함수 실행으로 재현

- 위치: `lib/3pl/orderGrouping.ts:115`, `:129`, `:185`, `:196`; `lib/3pl/epostService.ts:240`.
- A 작품 입고 → A만 송장 발급(`registered`) → 패킹 전 B 작품 입고 순서로 진행한다.
- 그룹화는 송장 발급된 A를 아직 활성 품목으로 본다. A/B가 모두 `received`가 되면 기존 A 그룹을 A+B 합포장으로 다시 만든다.
- 이 합포장 그룹은 마스터 주문에 저장된 A 전용 송장 `TRACK-A`를 상속하고 `submitted`가 된다.
- 따라서 화면의 작품 구성과 송장이 발급된 작품 구성·무게가 달라질 수 있다. 실제 택배 접수는 수행하지 않았고, 잘못된 그룹·송장 연결을 순수 함수로 확인했다.
- 개선안: 출고 묶음 ID와 품목·수량을 영속화하고 송장 발급 이후 고정한다. 변경하려면 기존 접수 취소·송장 재발급 절차를 거친다. 신규 합포장은 미배정 품목만 대상으로 계산한다.

### F02 · 높음 · 작가명 4자리 코드 충돌로 송장·완료 상태가 섞인다 — 함수 실행으로 재현

- 위치: `lib/utils/artistCode.ts:9`, `lib/3pl/orderGrouping.ts:111`, `:169`, `:285`.
- 작가명 해시를 4자리로 잘라 출고 이력 키에 사용한다. 서로 다른 `Artist A`와 `Artist B`가 모두 `1FS8`이다.
- 같은 주문에 두 이름이 존재할 때 A 송장만 있어도 B가 같은 송장을 참조한다. A의 fulfillment가 있으면 B도 완료로 분류되는 결과를 확인했다.
- 운영 데이터에 실제 충돌이 존재하는지는 조사하지 않았다. 생성 함수와 참조 구조의 충돌 가능성은 재현됐다.
- 개선안: 작가의 불변 ID와 독립적인 출고 ID를 사용한다. 외부 시스템용 짧은 번호는 별도 유일성 제약과 충돌 처리로 발급한다. 기존 키 이전 시 과거 송장·이력 연결을 보존한다.

### F03 · 높음 · 완료 기록 이후 로컬 처리 실패 시 재시도가 복구를 생략한다 — 정적 코드 확인

- 위치: `app/api/3pl/pack-complete/route.ts:47`, `:196`, `:211`, `:228`, `:272`.
- Shopify 성공 후 먼저 `packing_fulfillment_records.status = completed`를 기록하고, 이후 주문 품목·EMS 이력·마스터 상태를 갱신한다.
- 이후 갱신이 실패하면 최초 요청은 오류로 끝난다. 같은 요청 재시도는 앞부분의 `completed` 검사에서 성공을 반환해 남은 갱신을 실행하지 않는다.
- 결과적으로 외부 출고와 로컬 입고·출고 상태가 어긋날 수 있다. `upsert`와 일부 완료 기록 쓰기의 반환 `error`도 검사하지 않는다.
- 개선안: 외부 출고 성공과 로컬 정합성 완료를 구분하고, 로컬 갱신은 트랜잭션 또는 재실행 가능한 복구 단계로 처리한다. 중간 실패를 주입해 재시도 후 정상 수렴하는지 검증한다.

### F04 · 높음 · API가 출고 그룹 전체 준비 상태를 재검증하지 않는다 — 정적 코드 확인

- 위치: `lib/3pl/epostService.ts:75`, `app/api/3pl/pack-complete/route.ts:86`, `:247`.
- UI는 그룹 전체가 준비됐는지 보지만, API는 `received`인 품목만 조회해 한 건 이상 있으면 진행한다. 선택한 그룹의 모든 필수 품목이 준비됐는지 같은 규칙으로 재검사하지 않는다.
- 합포장/마스터 ID 요청은 일부만 입고되어 있어도 그 일부로 진행할 수 있다. 패킹 처리에서는 `parsedArtistName`이 없으면 `isAllPacked = true`로 시작하므로 미입고 품목을 남긴 채 마스터를 `PACKED`로 바꿀 수 있다.
- 개선안: 서버가 확정된 출고 묶음의 품목·수량·창고·검수 상태를 다시 검증해야 한다. 주문 전체 완료는 실제 남은 수량으로 판단한다. 화면이 오래된 경우와 직접 API 호출도 시험한다.

### F05 · 중간 · 한 주문 라인을 나눠 입고하면 누적 입고 완료로 연결되지 않는다 — 정적 코드 확인

- 위치: `lib/3pl/inboundService.ts:426`, `:523`.
- 주문 라인 전체 수량이 이번 입고 수량 이하일 때만 라인을 `received`로 바꾼다. 남은 수량은 물류 실물 재고에 더하지만 주문 라인에 부분 입고 수량으로 누적하지 않는다.
- 예: 수량 2개인 단일 대기 라인에 1개씩 두 번 입고하는 경우, 매번 `1 < 2`여서 이 경로에서는 라인을 입고 완료로 만들지 못한다. 실물 재고와 주문 준비 상태가 달라질 수 있다.
- 개선안: 주문 라인별 입고·출고 배정 수량을 관리한다. 같은 작가 일부 수량 선출고 허용 여부는 정책 결정이 필요하지만, 물리적 부분 입고를 기록하는 것은 별도로 필요하다.

## 3. 실행한 검증과 한계

어드민 디렉터리에서 `node --import tsx --input-type=module`로 실제 `groupArtistOrdersIntoSubOrders`와 `getArtistShortCode`를 불러왔다. 메모리상 가짜 주문과 빈 상품 맵을 사용했고, DB·외부 API는 연결하지 않았다.

| 입력 상황 | 확인 결과 |
| --- | --- |
| 서로 다른 코드의 두 작가 모두 입고, 송장 없음 | 합포장 1건, `ready` |
| A 입고, B 운송 중 | A `ready`, B `pending` |
| A 송장 발급, B 운송 중 | A `submitted`, B `pending` |
| A 송장 발급 후 B 입고 | **F01 재현: A+B 합포장에 A 전용 송장 상속** |
| A 출고 완료, B 입고; 작가 코드 서로 다름 | A `completed`, B `ready` |
| 작가명 `Artist A` / `Artist B` | **F02 재현: 둘 다 `1FS8`; 송장·완료 상태 교차 참조** |

첫 시험에서 `Artist A`/`Artist B`를 사용하다 충돌을 발견했고, 이후 코드가 서로 다른 `도자공방`/`목공방`으로 기본 시나리오를 분리해 다시 실행했다. F03–F05는 정적 검토 결과이며 DB 장애 주입이나 통합 시험으로 재현한 것은 아니다. 기존 전체 테스트·부하 시험도 실행하지 않았다.

## 4. 정책·후속 작업

- 입고 완료·검수 통과·취소되지 않은 주문 품목을 기준으로 출고 후보를 계산하는 방향을 문서에 제안한다.
- 접수 전에는 전체 입고 시 합포장, 일부 작가 입고 시 준비된 작가 선출고 후보로 제시한다.
- 접수로 확정된 묶음은 이후 추가 입고로 자동 변경하지 않는다.
- 현재 UI처럼 물류 작업자가 접수할 묶음을 선택하는 방식을 우선 논의한다. 선출고 자동 실행·대기 시간·추가 배송비 부담은 아직 합의하지 않았다.
- F01–F04를 우선 보완하고 부분 입고 수량·분할 배송 정책을 정한 뒤 F05를 검증한다. 기존 수정 중인 파일과 DB 적용 상태를 확인해 변경을 통합한다.
- 별도 확장성 검토 필요: `app/api/3pl/orders/route.ts:32`는 취소되지 않은 창고 주문을 페이지 제한 없이 조회하고 연관 데이터와 상품 목록을 조합한다. 이번 검토에서는 성능을 측정하지 않았으므로 IO 경고의 원인으로 단정하지 않는다.

이 보고서는 코드 검토 기록이며 기능 수정 완료 보고가 아니다.
