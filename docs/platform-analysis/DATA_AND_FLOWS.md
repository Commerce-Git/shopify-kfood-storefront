# 데이터 책임과 핵심 업무 흐름

2026-09-24 · A/F는 [기능 지도](FEATURE_MAP.md)의 저장소 표기. 실제 운영 DB 정의는 미확인이다. 아래 테이블·필드명은 소스 참조이며 DB 존재/제약 적용을 보증하지 않는다.

## 1. 현재 쓰기 경로와 책임

| 데이터 | 확인한 작성·변경 경로 | 책임 정리 및 차이 |
| --- | --- | --- |
| `artist_accounts` | 작가 가입·프로필·인증, 운영 계정 관리 | 인증 UUID와 업무 작가명이 공존. 거래 식별에는 불변 ID 필요 |
| `master_products` 가격·옵션·판매량 | 작가/운영 수정 API, Shopify 제품·재고 웹훅, 동기화 작업 | 양방향 쓰기 존재. 사용자 수정·주문 차감·외부 이벤트의 우선순위 필요 |

## 2. 상품 등록에서 구매 가능까지

`작가 인증 → 상품 등록/수정 → master_products → 운영 승인/Shopify 등록·동기화 → Shopify 카탈로그 → storefront 조회` 경로가 존재한다. 대표 경로는 A `api/artist/products/register`, `manage/approve-product`, `shopify/register`, `lib/shopify/publishProduct.ts`; F `lib/shopify/api.ts`다.

판매량 수정은 A `api/artist/inventory/bulk/route.ts:98`에서 버전 비교 후 저장하고 `sync_jobs`에 작업을 넣는다. `after()`에서 워커를 호출하며 별도 cron API도 있다. Shopify 재고 웹훅은 다시 `master_products` 수량을 갱신한다.

**확인 필요:** 작가의 설정, 구매로 인한 감소, 지연된 웹훅과 이미 큐에 든 이전 설정이 동시에 오면 어느 버전이 이기는가? 저장 성공 후 큐 적재 실패를 고객/작가 화면에 어떻게 표시하고 복구하는가?

## 3. 구매에서 주문·정산가 고정까지

- Shopify 주문 웹훅 → HMAC 검사 → `financial_status === 'paid'`인 경우 처리 → 현재 상품/옵션 가격 조회 → `artist_orders.settlement_price` 저장.
- 별도의 수집 경로 `runOrderCollector → upsertOrders`는 Shopify 주문을 `orders`에 저장한다.
- storefront 주문 조회는 Shopify 결과와 Supabase 주문 상태를 조합한다.

**차이:** 저장 후 현재 가격으로 다시 계산하지 않는 장치는 있으나 웹훅 지연 전에 작가가 가격을 바꿨을 때 구매 당시 가격을 선택하는 이력 조회는 확인하지 못했다. 웹훅에서 주문 라인 ID 대신 주문/SKU/옵션 제목을 충돌 키로 사용한다. 같은 SKU 반복 라인·주문 수정·미결제 생성 후 결제 완료 처리를 별도 검증해야 한다.

근거: A `app/api/shopify/webhook/orders/route.ts:26`, `:45`, `:141`, `:159`; `lib/pipeline/shared/order-manager.ts:26`.

## 4. 작가 발송에서 고객 배송까지

현재 `artist_orders.status`의 대표 흐름은 `pending → confirmed → shipped → received → shipped`다. 첫 `shipped`는 작가가 창고로 발송, 두 번째는 물류센터의 해외 출고 처리에서 사용한다. 포털은 `orders.sync_status`와 `ems_history`를 추가로 조합해 의미를 구분한다.

입고 완료 → 그룹화 → 작업자가 접수할 그룹 선택 → 우체국 송장 → 패킹 시 물류 재고 차감 → Shopify fulfillment → 로컬 상태 기록 순서다. 배달 완료는 17Track 웹훅이 EMS 이력을 갱신하고 Shopify 배송 이벤트를 추가하는 경로가 있다.

**필요한 계약:** 주문 라인별 입고/출고 수량, 고정된 출고 묶음 ID, 송장에 포함된 라인/수량, 입고·포장·운송사 인계·배달 완료 상태를 구분한다. 상태를 정리할 때 기존 고객 주문 화면과 정산 집계도 같이 수정해야 한다.

현 결함은 [물류 검토 F01–F05](2026-09-24-fulfillment-review.md)와 이번 진단에 연결한다. `auto-pipeline`은 물류 포털 경로와 다른 접수 경로이므로 동일한 입고 검증을 적용하는지 별도 확인한다.

## 5. 취소·반품·환불

F `api/cancel-order`는 인증·주문 소유권·취소 조건 확인 후 요청을 저장하고 Shopify 환불 계산→환불→취소를 수행한다. 부분 실패는 `review_required` 또는 `refund_completed_cancel_pending`으로 남긴다.

A의 취소 웹훅은 `artist_orders`와 `orders`를 취소로 바꾼다. 환불 웹훅은 `apply_shopify_refund` RPC에 refund ID와 SKU·옵션·수량을 전달한다. 읽은 환불 SQL은 물류 재고를 직접 변경하지 않는다. 프론트의 환불 요청에는 `restock_type: "cancel"`이 있어 Shopify 판매 재고와 역방향 웹훅에 미치는 영향을 별도 대조해야 한다.

작가 프로필의 `return_address` 필드는 존재하고 정산 정보 검증에 사용한다. 반품 사건별 주소 스냅샷·라벨·작가 수령·검수·반품 없는 환불을 통합한 업무 흐름은 이번 조사에서 증명하지 못했다. “필드가 있으므로 반품 기능 완성”으로 판정하지 않는다.

## 6. 정산 확정·지급·조정

작가/운영 정산 조회는 주로 `artist_orders`의 `shipped/received`, `payment_status`, `settlement_price`, `settled_amount`를 사용한다. 운영 API의 정산 완료 PATCH는 현재 과세 유형과 저장 단가로 금액을 산출해 paid 상태를 적는다. 이 API는 은행 이체 성공을 검증하는 코드로 볼 수 없다.

정산 취소 분기는 지급 시각·금액·세금 유형을 null로 지운다. 환불 RPC는 부분 환불 수량을 기존 주문 수량에서 뺀다. 결과적으로 원거래·지급 결과·환불 조정의 독립적인 감사 이력을 보장하는지 확인이 필요하다. 법률·세무 적합성은 이번 기술 검토의 확정 범위가 아니다.

핵심 미결정 정책: 구매 기준 사건, 지급 대상 확정 시점, 작가의 국내 발송과 고객 배달 완료 중 정산 기준, 지급 후 환불 공제, 음수 잔액, 실제 이체 결과의 대조 책임.

## 7. 장애·재시도·복구

서명 검증, 물류 수량 변경 RPC, 입고 요청 지문, 출고 중복 기록, 동기화 큐·워커 리스 등 기초 장치가 있다. 그러나 “한 부분의 중복 방지”가 “전체 업무의 정확히 한 번 처리”를 보장하지 않는다.

검증해야 할 중단점은 DB 저장 직후 외부 호출 전, 외부 성공 직후 DB 저장 전, 부분 라인 저장 후, 작업 claim 직후 프로세스 종료다. 외부 결과를 식별할 키와 로컬 미완료 단계를 보존하고, 재시도 후 원거래·실물 수량·송장·지급 내역이 수렴해야 한다.

## 8. 추가 확인한 전체 업무 연결

이번 2차 분석의 화면/API 근거는 [기능 등록부](FEATURE_MAP.md), 역할별 순서는 [사용자 여정](USER_JOURNEYS.md)에 연결한다. 아래는 코드에서 관찰한 현재 동작이다.

### 8.1 입점·공개 프로필·판매 게시

Kakao 로그인 → `artist_accounts` 조회 → join → `request-review`는 새 계정을 즉시 `approved`/`is_active:true`로 저장한다. 상품은 별도로 draft → pending_approval → 운영 승인 시 todo, 반려 시 rejected 전이를 거치며 Shopify 게시 경로가 따로 있다. 상품 검수 요청은 `isSettlementComplete`로 정산 정보와 반품 주소 등을 확인한다. **계정 활성화·정산 준비·상품 승인·외부 게시**는 서로 다른 사실이다.

F `lib/artists.ts`는 Shopify 상품의 작가 목록에 DB `artist_accounts`의 공개 필드를 합치며, 판매 상품이 없는 DB 작가도 목록에 추가하는 경로가 있다. A 프로필 수정은 DB/Storage 변경 후 프론트 재검증 API를 호출한다. 이름·slug·vendor·계정 ID의 관계와 비활성 작가 공개 범위는 후속 검증 대상이다. 현재 동작이 사용자 정책에 맞는지는 Q02/Q03에서 결정한다.

### 8.2 장바구니·고객 계정

장바구니는 브라우저 저장소에 보관하고 결제 시 variant ID·수량·쿠폰 코드를 Shopify `cartCreate`로 전달한다. 반환된 URL로 이동하기 전에 장바구니 복원용 백업을 저장한다. 주문·결제 완료의 기준은 브라우저 저장값이 될 수 없다. `NEXT_PUBLIC_STORE_LAUNCH_STATUS`가 live일 때 결제 동작을 실행하며 로컬 코드의 기본값은 preview다. 실제 배포 환경변수 값은 읽지 않았다.

고객 인증은 Supabase, 주문 조회는 인증된 이메일로 Shopify 주문을 찾고 DB 상태와 결합한다. 찜·팔로우는 로컬 상태와 로그인 후 DB 병합이 함께 존재한다. 이 조합의 계정 전환·탈퇴·주문 이메일 변경·지연 동기화 시나리오를 M01/M04/M05/M10 공통 계약으로 다룬다.

### 8.3 문의·알림·혜택

F Concierge → F `/api/inquiries` 프록시 → A 문의 API → `inquiry_threads`/`inquiry_messages` 및 첨부 Storage → 작가/운영 응답 → 고객 화면의 흐름을 확인했다. 프론트 프록시는 지정된 admin backend 한 곳으로 요청을 보낸다. 고객은 문의 토큰으로 접근하고 작가/운영 API는 역할 검증을 사용하므로 인증 방식이 서로 다르다. 토큰 보유 권한과 작가 귀속, 만료/회수, 공유 기기에서의 접근을 검증해야 한다.

뉴스레터·대기 목록은 Shopify 고객 태그/동의, 일부 Supabase 고객 정보와 연결한다. 리뷰는 `reviews`의 토큰 확인 후 Shopify 쿠폰 생성과 DB 저장·메일로 이어진다. Resend 이벤트와 수신 해지 경로가 고객/팔로우 상태를 갱신한다. 발송 요청·수신 동의·실제 전달·쿠폰 사용을 각각 구분하고 같은 사건의 재처리 기준을 확인해야 한다.

### 8.4 벤더 발주와 작가 판매량

`procurement` → Shopify 수량과 `inventory_settings` 비교 → 공급업체별 `purchase_orders`/`purchase_order_items` 생성 → vendor 토큰 포털 응답 → 운영 입고 확정 흐름을 확인했다. PO 상태는 DRAFT → SENT → APPROVED → SHIPPED → RECEIVED 또는 REJECTED다.

현재 PO 입고 확정은 Shopify의 해당 SKU 수량을 증가시킨다. 읽은 이 처리 경로에는 물류 `warehouse_inventory` 수불 기록 호출이 없다. 이 기능이 작가 주문 생산과 별개의 사입 상품을 위한 것인지, 같은 SKU에도 적용되는지는 Q04에서 정해야 한다. 안전재고/목표재고 설정을 작가가 정하는 판매 가능 수량의 상한으로 해석하지 않는다. 사용 대상과 실제 실행 여부를 확인하기 전에는 전체 재고 분리가 완성되었다고 판정할 수 없다.

### 8.5 내부 운영 자료

해외 법인 화면의 체크리스트는 localStorage, 확인한 계산·인쇄 도구는 컴포넌트 상태와 고정된 문서 템플릿을 사용한다. 공유 DB의 승인·지급·계약 원장으로 연결되었다는 증거는 없다. 해당 화면을 운영 참고 도구로 유지할지 공유 업무 기능으로 확장할지는 Q11에 포함한다. 화면에 포함된 법률·세무 문구의 적합성은 이번 소스 분석에서 검증하지 않았다.

## 9. 필드·사건별 변경 책임 초안

현재 호출 경로를 바탕으로 정리한 **책임 제안**이다. 공유 DB를 사용한다는 이유만으로 이 경계가 강제된 것은 아니다. 실제 DB 권한·RPC·트리거와 전체 API를 대조해야 한다.

| 데이터 영역 | 제안 주관 모듈·변경 사건 | 다른 모듈의 사용·제약 | 확인할 경계 |
| --- | --- | --- | --- |
| 인증 사용자·역할·창고 세션 | M01 로그인/권한 부여·회수 | 각 업무는 검증된 계정 ID/역할/창고 범위 사용 | 공개 가입·관리자 대리 작업·레거시 접근 코드·실제 RLS |
| `artist_accounts` 공개 정보·활성 상태 | M02 가입·프로필·개명·활성 변경 | M04는 공개 필드 조회, M05/M09는 거래 식별 참조 | 이름과 불변 ID 분리, 무상품/비활성 계정 노출 |

## 10. 모듈 사이의 계약 등록부

각 계약은 입력→결과와 실패 시 책임을 정하는 단위다. 아래 검증 기준은 초안이며 API 규격 확정·구현 완료를 뜻하지 않는다. 자세한 실제 경로는 기능 ID를 통해 찾는다.

| 계약 | 생산자 → 소비자 | 전달할 사실·기준 | 검증할 조건·미결정 |
| --- | --- | --- | --- |
| C01 계정·공개 정보 | M01/M02 → M03/M04/M09 | 인증 ID·역할·활성 상태·공개 프로필과 비공개 정보 경계 | Q02/Q03; 새 작가/비활성/개명/계정 전환에서 귀속·공개 일치 |
| C02 상품 판매 준비 | M02/M09/M03 → Shopify/M04 | 작가 자격·정산 준비·상품 승인·게시 결과 | J01; 승인 후 외부 게시 실패를 판매 중으로 표시하지 않음 |
| C03 판매량·가격 반영 | M03 → M11 → Shopify/M04 | 변경 버전·옵션 식별·수량/가격·외부 반영 결과 | Q05; 작가 설정과 주문·역순 이벤트·발주 입고 경합 |
| C04 구매 조건 확정 | Shopify → M05 → M09 | 외부 주문/라인 ID·시점·수량·정산 단가 근거 | Q06; 지연·중복 주문·가격 수정 후에도 구매 당시 조건 보존 |
| C05 작가 발송·물류 입고 | M05 → M06 | 주문 라인·창고·예정 수량·국내 송장 → 누적 검수/배정 수량 | Q07; 일부/중복 입고·격리·되돌림 수량 대조 |
| C06 출고·고객 표시 | M06 → M07 → Shopify/M05/M04 | 검수 통과·출고 라인/수량·고정 묶음·송장·운송 사실 | J02; 추가 입고·부분 출고·외부 성공 후 로컬 실패에도 같은 배송 표시 |
| C07 취소·반품·환불 | M08 ↔ Shopify/M05/M07/M09 | 취소/환불 ID·대상 수량/금액·반품 주소·수령 사실 | Q08/Q09; 미출고 중지와 금전/물류 조정을 구분 |
| C08 정산·지급 | M05/M08 → M09 → 작가/운영자 | 원거래·조정·대상 확정·지급 확인·증빙 | Q09; paid 표시와 은행 사실 대조·중복 지급 방지 |
| C09 고객 문의 | F M10 → A M10 → 작가/고객 | 문의 토큰·작가 귀속·메시지/첨부·번역·읽음·알림 | J04; 지정 환경 연결, 권한·재전송·번역/메일 실패 복구 |
| C10 고객 관계·혜택 | M10 ↔ Shopify/Supabase, M11 전달 | 고객 ID·수신 의사·찜/팔로우·리뷰·쿠폰 발급/사용 | Q10; 계정 병합·해지·쿠폰 생성 후 저장 실패 대조 |
| C11 공급업체 발주 | M03-F004 ↔ 공급업체/M06/M03-F003 | PO·SKU·발주/실제 입고 수량·외부 판매량 반영 | Q04; 사입/작가 판매 유형 식별, 이중 증가·누락 방지 |
| C12 이벤트·운영 | 업무 모듈 ↔ M11/M12 | 외부 이벤트 ID·처리 상태·재시도·오류·배포/DB 적용 버전 | J07; 중단 작업 회수·미실행 스케줄 탐지·사용자 영향 관측 |

코드 분리 후보는 이 계약의 중복 규칙을 기준으로 정한다. 예를 들어 M10은 문의·고객 관계·혜택, M03은 작가 상품·벤더 발주로 세분할 수 있다. 사업 범위와 결합도를 확인한 후 기존 M ID의 하위 기능부터 분리하며 모노레포·서비스 분리를 전제하지 않는다.
