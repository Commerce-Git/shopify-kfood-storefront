# BLANK SEOUL — 전체 플랫폼 분석·검증 계획

작성일: 2026-09-24 · 버전: 0.3 · 상태: 2차 역할별 여정·기능 분석, 전체 검증은 미완료

실행 결과: [플랫폼 분석 기준 문서](README.md). AP00–AP06별 실제 수행/미수행 상태, 소스 기준선, 테스트와 결함 근거는 결과 문서를 따른다.

현재 후속 분석은 [모듈별 관리 기준](FEATURE_MAP.md)과 [로드맵 0절](IMPROVEMENT_ROADMAP.md)을 따른다. 1차 정적 목록·선별 검토를 전체 상세 분석 완료로 간주하지 않고, 역할별 목표와 M01–M12의 기능·책임·연동·검증 범위를 먼저 보완한다.

2차 산출물: [사용자 여정](USER_JOURNEYS.md)에 5개 역할·33단계·J01–J07 인수 시나리오, 기능 지도에 35개 기능, 데이터 문서에 C01–C12 계약을 작성했다. Q01은 한국 제조 상품 우선·K-Food 보류까지 사용자 결정(D016)을 반영했다. 나머지 정책과 실제 운영 적용은 각 질문의 미확정/미검증 범위를 유지한다.

목표와 운영 원칙의 원본은 [PROJECT_DIRECTION.md](PROJECT_DIRECTION.md)다. 이 문서는 그 목표가 프론트·어드민·DB·배포 환경·외부 연동에 구현되어 있는지 확인하는 방법을 정의한다. 기존 요구사항을 중복 관리하지 않고 R01–R12를 참조한다.

## 1. 분석 방식

**전체 구조 파악 → 업무 모듈과 데이터 책임 구분 → 실제 업무 흐름 추적 → 목표 대비 차이 판정 → 위험순 개선 → 재검증** 순서로 진행한다.

전체 기능의 목록과 연결 관계는 먼저 넓게 조사하고, 주문·돈·재고·접근 권한처럼 영향이 큰 경로부터 깊게 검증한다. 모든 파일을 같은 깊이로 읽거나 모든 정책 답변이 나올 때까지 분석을 미루지 않는다. 확인하지 않은 영역은 명시적으로 남긴다.

업무를 논리적으로 모듈화하는 일과 코드를 물리적으로 분리하는 일은 구분한다. 이번 분석의 출발점은 기능·책임·의존성을 정리하는 것이다. 폴더 이동, 공통 패키지 도입, 모노레포 전환, 서비스 분리는 분석으로 필요성이 드러난 경우에 비교한다. 구조 변경 자체를 완료 목표로 삼지 않는다.

## 2. 조사 범위와 확인할 증거

| 대상 | 조사할 내용 | 필요한 증거 |
| --- | --- | --- |
| storefront | 페이지·API·구매 흐름·캐시·인증·개인정보·외부 호출 | 실제 코드 경로, 관련 테스트, 배포 버전 |

로컬 코드만으로 운영 Supabase/Vercel까지 확인했다고 판정하지 않는다. 운영 접근이 없으면 코드·SQL 기반 분석을 진행하고, 필요한 설정·지표를 묶어 요청한다. 비밀값이나 고객 원문 데이터를 문서에 복사하지 않는다. 현재 활성 IO 장애가 있다면 진단·피해 제한을 우선한다.

기존 방침대로 운영 SQL 실행·마이그레이션 적용·Git push는 사용자가 직접 한다. 운영 자료는 대시보드·읽기 전용 수단·사용자가 제공한 결과로 조사한다. 부하 시험과 외부 상태 변경은 독립된 시험 환경·범위를 먼저 정한다.

## 5. 목표 대비 판정표

`요구사항 → 모듈 → 코드·DB·운영 설정 → 검증 시나리오 → 실행 증거 → 판정 → 개선 작업`을 연결한다.

| 요구사항 | 현재 근거 예시 | 판정 예시 | 다음 증거 |
| --- | --- | --- | --- |
| R12 합포장·작가별 선출고 | 로컬 그룹화 함수와 2026-09-24 재현 결과 | 부분 충족: 기본 경로 확인, F01/F02 결함 재현 | 수정 후 그룹화 회귀 시험 및 접수·출고 통합 검증 |
| R06 구매 당시 정산가 | 요구사항만 확정; 관련 정산 문서 일부 확인 | 정책 일부 미결정·구현 검증 필요 | 가격 이력·주문 경로·지연 웹훅 시험 |
| R07/R10 동시 이용 | 동시 사용자 목표만 확정 | 성능 미검증 | 실제 사양·요청 모델·장시간 부하·비용 결과 |
| R09 IO 경고 예방 | 사용자 경고 보고 | 원인 미확정 | 발생 시각과 쿼리·작업·디스크 지표 대조 |

판정 용어:

- **충족:** 합의한 범위·조건에서 필요한 증거가 확보됨. 환경·버전·시점을 함께 적는다.
- **부분 충족:** 일부 경로는 있으나 누락·결함·검증 부족이 있음.
- **미충족:** 합의한 요구와 충돌하거나 필요한 기능이 없음.
- **미검증:** 증거 부족으로 판단할 수 없음.
- **정책 미결정:** 기대 동작 자체를 결정해야 함. 현재 동작은 별도로 기록한다.
- **해당 없음:** 적용하지 않는 이유를 기록한다.

정책 확정 여부와 구현·검증 상태는 별도 열로 관리할 수 있다. 파일 존재, 주석, 예전 PASS 보고, 빌드 성공만으로 요구사항 충족을 선언하지 않는다. 보안·돈·재고 결함은 평균 점수로 상쇄하지 않는다.

## 6. 수행 단계와 종료 기준

### 6.1 실측한 초기 조사 규모

2026-09-24 로컬 파일명 기준으로 storefront는 `page.tsx` 21개·API `route.ts` 24개, admin은 각각 24개·125개다. `supabase/` 아래 SQL 파일은 각각 13개·44개다. 이 수치는 조사 규모의 참고값이며, API 메서드별 기능 수·배포된 경로 수·실제 DB 객체 수가 아니다. 미사용 코드·동적 경로·공유 서비스·스크립트·DB 내부 작업은 목록화 단계에서 추가 조사한다.

storefront에는 `vercel.json`이 있지만 admin에는 없고, 양쪽 모두 로컬 `.vercel/project.json`은 발견하지 못했다. 이 사실만으로 Vercel 배포 여부를 판단하지 않는다. 운영 프로젝트와 배포 연결은 AP04에서 확인한다.

| 4 · AP04 | 실제 Supabase/Vercel/Shopify/배송 설정·배포 버전과 로컬 구현을 대조. IO 경고·장애·재시도·백업 현황 확인 | 운영 환경 대조표·성능 기준선 | 환경별 확인 항목마다 근거 또는 미검증 사유가 있고 IO 진단 결과/추가 자료가 정리됨 | AP01부터 접근 자료 수집 가능; 운영 자료 미확인 |
| 5 · AP05 | 핵심 흐름 시험, 장애·동시성·권한 검증 계획과 실제 실행 결과를 정리. 20,000세션 부하 모델·비용·용량 검증 계획 작성 | 검증 계획·결과·미실행 목록 | 실행 환경·데이터·명령·판정 기준·결과가 구분되고, 실행하지 않은 시험을 성공으로 처리하지 않음 | AP03/AP04 근거 사용; 환경 의존 시험은 별도 일정 |
| 6 · AP06 | 위험도·의존성·사용자 영향에 따라 작업 순서 결정. 필요한 모듈화 범위와 배포·복구 절차 설계 | 우선 개선 목록·구조 개선 제안·실행 순서 | 각 작업에 요구사항, 수정 대상, 선행 조건, 완료 시험, 수동 적용 항목이 있음 | 1차 분석 마지막 단계 |

AP04의 자료가 늦어져도 로컬 AP01–AP03을 계속한다. 정책 미결정도 해당 분기의 기대 결과만 보류하고 다른 경로 분석을 막지 않는다. 새 결함으로 바뀐 코드가 있으면 기준선 차이를 기록하고 영향받은 부분을 재검토한다.

### 6.3 상세 검토 순서

1. **주문·돈·재고:** 주문 수신과 정산가 스냅샷 → 작가 판매 가능 수량/물류 재고 → 입고·출고 → 취소·환불 → 정산·지급을 연결해 검토한다.
2. **접근 권한:** 위 경로마다 구매자·작가·창고·관리자 경계를 동시에 확인한다. 보안 검토를 기능 검토 종료까지 미루지 않는다.
3. **운영 지속성:** 중복·지연·역순 이벤트, 재시도, 부분 실패, 누락 대조, DB 제약과 복구를 확인한다.
4. **나머지 기능:** 카탈로그·검색·문의·알림·리뷰·프로모션·SEO 등 발견한 기능을 검토하고 출시 필수/후속 개선 범위를 제안한다.
5. **성능·비용:** IO 원인 후보·쿼리·캐시·폴링·큐·외부 제한을 조사한다. 정상 처리의 정합성을 확인한 뒤 최대 부하 시험을 진행한다.

물류 검토 F01–F05는 알려진 조사 항목으로 가져오고, 전체 코드의 변경 여부와 재현 근거를 확인한다. 한 분야의 결함 수만으로 다른 분야보다 우선하다고 판단하지 않는다.

### 6.4 판정과 개선 우선순위

| 우선순위 | 기준 | 처리 방식 |
| --- | --- | --- |
| P0 | 실제 운영 중 정보 노출·잘못된 지급·주문 손실·서비스 중단 등 즉시 피해가 확인됨 | 사용자에게 즉시 알리고 해당 경로 진단·피해 제한을 우선 |
| P1 | 현실적인 조건에서 금액·재고·배송·권한 오류 또는 복구 불가능한 실패 발생 | 해당 기능의 출시/확장 전 해결할 과제로 지정 |
| P2 | 성능·운영 효율·유지보수·일부 UX 문제 | 측정한 영향과 비용에 따라 순서 결정 |
| P3 | 기능 확장·장기 구조 개선 | 핵심 안정성 확보 후 검토 |

위험도와 증거 확실성은 별도 기록한다. 각 결함에는 재현 조건, 영향 대상, 코드/설정 위치, 증거 종류, 관련 요구사항, 권장 조치와 회귀 시험을 붙인다. 원인 가설을 운영 장애 원인으로 확정하지 않는다.

### 6.5 사용자와 논의할 시점

- **AP01/AP02 결과:** 빠진 사업 기능과 실제 업무 책임을 확인한다. 먼저 코드에서 알아낼 수 있는 내용은 조사한다.
- **AP03 결과:** 정산 기준 시점, 선출고·대기·추가 배송비, 취소 수량 복원처럼 운영 의사결정이 필요한 항목을 업무별로 묶어 제시한다. 현재 동작·선택지·영향·권장안을 함께 적는다.
- **AP04/AP05 준비:** 접근이 없을 때만 Supabase/Vercel 등의 설정·지표·시험 환경 정보를 묶어 요청한다. 운영 비밀값 공유를 요청하지 않는다.
- **AP06 결과:** 출시 전 해결할 문제와 이후 개선할 항목, 비용이 수반되는 선택을 정한다. 기술적으로 이미 결정 가능한 수정까지 반복 확인을 요구하지 않는다.

분석 단계는 Codex가 조사와 근거 정리를 담당한다. 후속 구현에서는 검증된 agent-bridge 범위에서 Gemini에 작은 작업을 전달하고, 실행기의 테스트 결과와 실제 diff를 확인한다. 두 저장소 지원이 검증되기 전에는 자동화가 이미 가능하다고 가정하지 않는다.

### 6.6 분석 완료와 운영 준비 완료

1차 분석의 완료 조건은 모든 위험의 제거가 아니라 **조사 범위의 기능·연동 목록, 핵심 흐름 근거, 요구사항 판정표, 미검증 목록, 우선순위가 있는 개선 작업**이 준비된 상태다. 출시 준비 완료는 이후 핵심 결함 해결·운영 검증으로 별도 판단한다.

분석 결과 제출 시 AP00–AP06별 수행/부분 수행/미수행과 사유를 공개한다. 운영 접근이나 시험 환경이 없으면 로컬 분석 결과를 제공하되 운영 적합성 평가는 미완료로 남긴다. 일정은 AP01에서 실제 호출 관계·DB 중복·기존 테스트 수준을 파악한 후 산정하며, 파일 수만으로 전체 완료일을 약속하지 않는다.

2만 명 동시 이용은 조회·구매·입고·정산의 사용 비율과 대표 데이터량을 정한 뒤 부하 시험한다. 초기에 필요한 운영 수용량과 장기 목표를 구분하되, 사용자 합의 없이 목표를 축소하지 않는다. 용량·비용은 측정 근거로 선택한다.

## 7. 모듈화 개선의 판단 기준

물리적 코드 변경은 다음과 같은 문제를 해결할 때 제안한다.

- 같은 업무 규칙이 프론트·어드민·API·DB에서 다르게 적용된다.
- 한 변경의 영향을 찾기 어렵거나 여러 저장소의 수정이 반복적으로 누락된다.
- 외부 API·DB 연결 없이는 핵심 업무 규칙을 시험할 수 없다.
- 여러 경로가 같은 데이터를 각자 갱신해 동시성·재시도 오류를 만든다.

우선은 기존 두 프로젝트 안에서 업무 규칙·데이터 접근·외부 연동의 경계를 명확히 하고 공통 계약을 맞추는 방안을 검토한다. 모노레포나 별도 서비스 도입은 배포 독립성·코드 공유·운영 부담을 비교해 필요할 때 결정한다.

## 8. 기록·유지 방식

- `PROJECT_DIRECTION.md`: 사용자가 결정한 목적·운영 원칙·미결정 사항.
- 이 문서: 전체 분석의 범위·절차·판정 기준.
- AP00–AP06 결과: 아래 구조로 기록하고 공통 ID로 연결한다. 파일은 실제 조사 결과가 생길 때 생성하며 빈 문서의 존재를 진척으로 계산하지 않는다.
- `2026-09-24-fulfillment-review.md`: 같은 폴더에 보관한 기존 물류 검토의 상세 증거. F01–F05를 재활용하고 재검토 시 새 버전과 결과를 기록한다.
- `.agent-bridge/COMMAND.md`, `REPORT.md`, `REVIEW.md`: 이번에 실행할 작업과 그 결과. 작업 단위 기록을 장기 목표 문서와 연결한다.

각 분석 기록에는 조사일·저장소/배포 버전·실제 읽은 범위·검증 방식·미확인 사항을 적는다. 이후 변경이 생기면 영향받은 모듈과 흐름을 우선 재검증한다. 매번 전체를 처음부터 분석하지 않는다.

예정 산출물 경로:

```text
docs/platform-analysis/
  README.md                 # 진행 상황, 조사 기준선, 주요 결론
  PROJECT_DIRECTION.md      # 공통 목표·운영 원칙·결정 기록
  PLATFORM_ANALYSIS_PLAN.md # 분석 범위·절차·완료 기준
  USER_JOURNEYS.md          # 역할별 여정·인수 시나리오·정책 질문
  FEATURE_MAP.md            # 전체 기능·모듈·코드 경로 목록
  DATA_AND_FLOWS.md         # 데이터 책임, 상태 전이, 업무 흐름
  REQUIREMENTS_MATRIX.md    # 요구사항별 정책/구현/검증 판정
  FINDINGS.md               # 근거·재현·영향·우선순위가 있는 결함 목록
  OPERATIONS.md             # 실제 배포·DB 설정·운영 지표와 미확인 사항
  VALIDATION.md             # 검증 계획·실행 결과·성능/복구 시험 범위
  IMPROVEMENT_ROADMAP.md     # 수정 순서·의존성·완료 조건·수동 적용
  2026-09-24-fulfillment-review.md # 기존 물류 상세 검토
  SOURCE_INVENTORY.md       # 최초 전체 소스 목록
  inventory.json           # 최초 소스 기준선·정적 참조
  check-results.json       # 1차 실제 검사 결과
  journey-evidence.json    # 2차 진입점 분류·참조·해시·문서 확인 결과
```

모든 문서는 storefront의 공통 문서 위치를 원본으로 유지하되, admin 관련 항목에는 대상 저장소를 명시한다. `FEATURE_MAP`은 경로 목록, `REQUIREMENTS_MATRIX`는 판정, `FINDINGS`는 결함 상세를 맡고 서로 링크해 중복 갱신을 줄인다. 실제 코드 수정은 이 분석 결과를 근거로 작업 단위로 이어간다.
