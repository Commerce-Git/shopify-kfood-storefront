# BLANK SEOUL 플랫폼 분석 — 기준 문서

분석일: 2026-09-24 · 버전: 2차 로컬 분석 v0.2 — 사용자 여정·기능·책임 연결

프론트·어드민을 하나의 서비스로 보고 기능·데이터·요구사항·개선 작업을 연결한 문서다. 이후 개발자는 이 문서에서 시작해 관련 요구사항과 실제 코드 근거를 확인한다.

목표·계획·분석·검증·개선 관련 문서 원본은 **`docs/platform-analysis/` 한 폴더**에서 관리한다. 두 프로젝트에서 이 목차를 참조하며 문서 복사본을 따로 만들지 않는다.

**현재 사업 방향:** 한국 제조 상품을 중심으로 진행한다. K-Food는 통관과 작가 모집의 어려움 때문에 추후로 보류했다. 궁극적 목표·과거 전략의 참조 범위·남은 결정은 [목표 문서 D015/D016](PROJECT_DIRECTION.md)에 기록한다. 이번 사업 범위 확정으로 기존 코드가 변경되거나 검증된 것은 아니다.

**현재 결론:** 구매자·작가·물류·운영자와 추가 공급업체 역할의 흐름을 12개 모듈·35개 기능 묶음에 연결했다. 입점과 상품 승인, 작가 판매량과 벤더 발주, 공개 프로필과 정산 정보 등 책임을 구분할 기준이 필요하다. 기존 거래·물류·복구 결함은 해당 기능의 개선 항목으로 유지한다. 운영 DB·배포 설정과 20,000명 동시 이용은 미검증이며 출시·대규모 운영 적합 판정을 내리지 않는다.

## 작업 시작 시 확인할 기준

1. **목표와 범위:** 한국 제조 상품을 중심으로 작가의 안정적인 판매·정산, 구매자 신뢰, 감당 가능한 비용·인력으로 거래를 반복·확장한다. 확정된 운영 원칙과 20,000명 동시 이용 목표는 `PROJECT_DIRECTION.md`를 따른다.
2. **현재 초점:** 전체 모듈 평가를 바탕으로 목표→성공 지표→필요한 역량→구현/검증 작업을 연결한다. 상품군·시장·지표의 미결정 부분은 질문으로 남기고 독립적인 코드·데이터 분석은 진행한다.
3. **진행된 범위:** 역할·기능·계약의 로컬 분석 초안은 작성됐다. 같은 목록화를 반복하기 전에 변경된 코드와 남은 검증 범위를 확인한다. 운영 DB·배포·E2E·부하 검증은 미완료다.
4. **작업 선택:** 어떤 목표에 기여하는지, 어떤 모듈/여정에 영향을 주는지, 왜 지금 필요한지, 완료 증거가 무엇인지 설명한다. 사용자 제안도 이 기준으로 검토하고 더 적합한 방법이 있으면 근거와 함께 제안한다.

| 직접 선언된 HTTP 핸들러 | 34 | 178 |
| 수집 범위 SQL 파일 | 15 | 66 |
| 스크립트 파일(SQL 제외) | 7 | 254 |

파일 수는 코드의 품질·테스트 커버리지를 의미하지 않는다. admin의 스크립트에는 다수 시험·과거 라우트가 있으며 현재 API로 세지 않았다. SQL은 `supabase/`, `lib/`, `scripts/`를 포함한다. 이전의 supabase 폴더만 센 집계와 범위가 다르다.

양쪽 저장소에 기존 미커밋 변경이 있다. 그 내용을 포함한 작업 트리를 조사했으며 배포된 버전이라고 가정하지 않았다. 시작 시 변경 목록과 수집 소스의 SHA-256은 [inventory.json](inventory.json)에 보존했다. 원문 전체나 환경변수 값은 저장하지 않았다.

## 1차 분석에서 수행한 범위

- `app/lib/scripts/supabase/tests/types/.github/workflows` 및 주요 설정을 정적으로 목록화했다. 동적 참조·간접 의존성은 자동 추출만으로 확정하지 않았다.
- 주문 수신·취소·환불·정산, 재고 설정·동기화 큐, 물류 그룹화·출고, 공통 인증 및 고객 주문 접근 경로를 선별해서 읽었다.
- 기존 단위 테스트: storefront 9/9, admin 15/15 통과. 양쪽 타입 검사 통과.
- 실제 물류 도메인 함수 진단: 7개 검사 중 5개 통과, 2개 실패로 기존 결함 재현.
- 외부 운영 시스템에 연결된 분석 도구는 현재 세션에서 확인되지 않았다. 운영 DB 조회·SQL 적용·실제 결제/배송·Git push는 수행하지 않았다.

모든 라우트를 수집한 것과 모든 라우트의 동작·보안을 감사한 것은 다르다. 문의·프로모션·통관·조달 등은 기능 존재와 의존성 위주로 분류했고 상세 동작은 추가 검토 대상이다.

### 2차 분석에서 추가한 것

- 역할별 33단계(B01–B09/A01–A09/L01–L06/O01–O08/S01), 모듈을 가로지르는 J01–J07 인수 시나리오 작성.
- 35개 기능의 대표 화면→hook/API→데이터·외부 호출 연결, 전체 페이지 45개·라우트 파일 150개의 주관 모듈 분류.
- 필드·사건별 책임 초안과 C01–C12 계약, 사업 정책 질문 Q01–Q12 작성. 실제 코드 경계를 변경하거나 사업 정책을 임의 확정하지 않음.
- [journey-evidence.json](journey-evidence.json)에 진입점·API 문자열 참조·코드 해시 저장. 최초 수집 1,062개 파일의 변경/누락 0건 확인. 과거 검사 결과를 다시 실행한 결과로 표기하지 않음.

AP01의 진입점 분류와 AP02의 대표 여정 연결 범위를 확장했다. 동적 호출·전체 분기·실제 DB와 배포 대조·통합 시험은 계속 미완료다.

## 다음 작업자가 따라야 할 방식

1. 목표 문서에서 관련 R번호와 미결정 정책을 확인한다.
2. 이 분석의 기준선과 현재 코드를 비교한다. 특히 미커밋 변경을 덮어쓰지 않는다.
3. 관련 요구사항·기능·여정/계약·로드맵 작업 ID를 지시에 적고, 대상 저장소·DB·배포 영향·완료 시험을 명시한다. 결함 수정이면 해당 결함 ID도 연결한다.
4. 변경 후 실제 diff와 검사 결과를 남기고 해당 판정만 갱신한다. 파일 존재·과거 PASS만으로 완료 처리하지 않는다.
5. SQL 파일 작성·검토는 가능하며 적용과 Git push는 사용자 수동 방침을 유지한다.

## 현재의 다음 단계 — 출시 범위 논의와 계약별 미확인 부분 검증

개별 배송 결함부터 수정하는 제안은 전체 평가 후 순서를 정하는 방식으로 보정했다. 2차 분석으로 역할별 여정·기능·계약 초안을 만들었으며 모든 모듈의 상세 분석 완료를 뜻하지 않는다.

1. [목표 문서](PROJECT_DIRECTION.md)의 합의된 방향을 기준으로 한국 제조 상품 안의 우선 상품군·고객 가치·판매 시장·제조 확인 기준을 구체화한다. Q01의 한국 제조 상품 우선·K-Food 보류는 확정 사항으로 유지한다.
2. M01–M12의 미확인 부분을 C01–C12 계약별로 좁혀 조사한다. 공개/비공개 정보, 상태 전이, 간접 쓰기와 중복 규칙을 확인한다.
3. J01–J07 흐름의 시험 조건을 정하고 Supabase·Vercel·Shopify 운영 자료를 코드와 대조한다. 운영 자료가 없어도 독립적인 로컬 조사는 계속한다.
4. 전체 범위의 누락·중복 책임·목표 대비 차이를 정리한 뒤 구현 순서를 선택한다. 결함 목록은 그 판단의 근거로 유지한다.

구현 착수 판단 기준은 [개선 로드맵](IMPROVEMENT_ROADMAP.md)의 0절을 따른다. 실제 운영 사고가 확인되면 영향과 예외 작업을 기록하고 우선 대응한다.
