### 1차 설정·표현 구현과 검증 — 2026-11-06

사용자가 첫 작업 범위를 설정·표현 정리로 선택하고 구현을 요청했다. **이 범위의 코드·개발 검증은 완료했으며 인증·주문 접근 검증은 다음 작업으로 남긴다.** 기존 반품 안내의 미커밋 수정과 다른 Admin 작업을 보존했다.

- 홈페이지·고객 정책에서 사용하는 `BUSINESS`를 이메일 5종에서도 참조하도록 `SellerIdentity`를 추가했다. 상호·주소·지원 이메일을 공통 표시하고 입력 타입·수신거부 URL·발송 헤더를 변경하지 않았다. 중지된 sender 4개는 계속 no-op다. [이메일 구현 원본](../../emails/EMAIL_PIPELINE.md)을 따른다.
- 환불 소요 기간과 체크아웃 비용 안내는 `lib/config/customer-service.ts`의 공통 문구를 사용한다. 정책·취소 화면의 고정 은행 처리 일수, 장바구니의 세금 포함/통관 완료 단정, FAQ의 국가별 무관세 단정을 정리했다. 체크아웃 안내는 **판매자가 징수하는** 세금·관세에 한정하며 모든 수입국 추가 비용을 확정한다는 의미로 사용하지 않는다.
- 취소 시간의 약관·반품 제목·메타데이터를 기존 `CANCEL_WINDOW_HOURS`에 연결했다. 기존 30일 보장·무료배송 조건은 유지하고 배송 예시는 해당 서비스가 체크아웃에 제공될 때의 추정으로 표시했다. 새로운 판매국·요율·계약을 결정하지 않았다.
- Admin `/3pl` 하단은 `BLANK SEOUL` 브랜드로 표시한다. 클라이언트 화면에 우체국 서버 설정이나 다른 저장소 코드를 import하지 않는다. 과거 LLC·계약 기록은 보존했다.
- 내부 이메일 안내의 도메인 인증 완료·법적 준수 보장을 확인 목록과 구현 설명으로 바꿨다. 템플릿 표시와 실제 발신 도메인 인증·배달 성공을 구분한다.

## 의존성 검토

Next.js 16.2.3 → 16.3.8 및 같은 버전의 eslint-config-next로 업데이트했다. [공식 이미지 최적화 보안 공지](https://github.com/vercel/next.js/security/advisories/GHSA-cjq9-62q9-8jv4)와 npm advisory의 수정 범위를 확인했으며, semver 범위 내 전이 의존성 수정도 적용했다. 변경 후 단위·타입·린트·빌드와 구매 브라우저 시험을 확인한다.

후속 요청에 따라 `@react-email/ui`가 고정한 Next 16.3.3을 `package.json`의 범위 한정 override(`@react-email/ui.next: "$next"`)로 앱과 같은 16.3.8에 연결했다. 다른 도구의 Next를 일괄 덮어쓰지 않는다. 깨끗한 `npm ci` 후에도 내부 Next가 16.3.8로 연결됨을 확인했다. 미리보기 서버 기동과 주문 취소·쿠폰 확인 메일의 실제 브라우저 렌더링, 단위45개·타입·린트·TEST 환경 빌드를 확인했으며 메일 발송은 하지 않았다. upstream이 수정 버전을 제공하면 이 override의 필요성을 다시 확인한다.

최초 후속 감사의 잔여 high 5건은 `eslint-config-next → @next/eslint-plugin-next → fast-glob → micromatch → braces`라는 한 경로에서 발생했다. [braces 공식 보안 공지](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)는 검토 시점에 수정 버전이 없었다. 이후 사용자 요청으로 이 의존성 경로를 제거했다. **최종 깨끗한 `npm ci`와 전체 `npm audit` 결과는 0건**이다. upstream braces 자체를 수정했다는 뜻은 아니다.

Next ESLint 플러그인의 실제 호출은 `get-root-dirs.js`의 `globSync(string, { onlyDirectories: true })`뿐이다. 해당 버전 아래의 fast-glob만 로컬 어댑터 `tools/next-eslint-glob`로 연결하고 tinyglobby 0.2.17로 처리한다. 단순 패키지 alias는 절대/상대 경로와 단일 디렉터리 확장 동작이 달라 채택하지 않았다. 어댑터는 이 차이를 보정하고 예상하지 못한 인자를 거부한다. `rootDir`의 문자열·배열·와일드카드·중괄호·숨김·불일치와 실제 Next 링크 검사 규칙을 검증했다. 린트 규칙을 끄거나 감사 경고를 숨긴 것이 아니다.

이것은 전체 fast-glob API 대체재가 아니다. Next/ESLint 갱신 시 호출 규격과 override 적용 범위를 재검토하고 공식 해결이 제공되면 제거한다. [어댑터 유지관리](../../tools/next-eslint-glob/README.md)를 따른다.

## 현재 인증 유지 시 운영·로컬 점검 (2026-10-25)

사용자가 기존 인증 유지 방향에서 현재 문제가 없는지 확인을 요청했다. Shopify 고객 인증으로의 전환, 운영 인증 설정·DB 변경·이메일 발송·실제 결제는 이번 범위가 아니다. 다음의 운영 관찰과 로컬 시험을 구분한다.

### 운영 사이트에서 직접 확인

- `https://blankseoul.com/account/login`과 `/order-lookup`이 정상 표시되고, 비로그인 `/account`는 로그인 페이지로 이동했다. 이 세 경로에서 수집한 브라우저 페이지 오류는 0건이다.
- 운영 Google 로그인 버튼은 실제 운영 Supabase(`feezosccyvecmrhqrkgl.supabase.co`)의 Google 인증을 시작하며 반환 주소는 `https://blankseoul.com/auth/callback`이다. 별도 읽기 전용 확인에서 Google 로그인 화면까지 이동했다. Google 자격 증명 입력·로그인 완료는 하지 않았다.
- `.env.local`은 TEST Supabase와 dev Shopify, `.env.production.local`은 운영 Supabase와 운영 Shopify를 가리킨다. 실제 운영 브라우저 인증 호스트까지 대조했으므로 개발 환경 설정만 보고 운영 인증을 판단한 것이 아니다. 인증값은 기록하지 않았다.
- 비로그인 `/api/orders` GET과 `/api/track-order` POST는 모두 401을 반환했다. 주문이나 고객 개인정보는 조회하지 않았다.
- 로그인 취소를 나타내는 `/auth/callback?error=access_denied`는 `/account/login?error=auth_failed`로 돌아오지만, 운영 로그인 화면에는 실패·재시도 안내가 없었다. 실제 계정 실패율이나 로그인 자체 불가를 의미하지 않는다.
- `https://account.blankseoul.com/`은 브라우저에서 기존 `shopify.com/authentication/.../login`으로 이동하며 Shopify 로그인 화면이 표시됐다. 사용자가 제공한 도메인 화면의 연결·TLS 완료 및 기존 계정 주소로 리디렉션하는 유형과 일치한다. 새 기본 도메인 적용·Supabase와의 로그인 통합은 확인된 사실이 아니다. 단순 HTTP 도구는 403을 반환했으므로 이 응답을 도메인 장애로 판정하지 않았다.

사용자 결정대로 커밋·푸시·배포는 수행하지 않는다. 추후 수정본을 dev에 배포한 뒤 실제 두 테스트 계정의 주문/로그아웃, 리뷰 쿠폰·구독 저장, 구매→어드민 주문 수신을 확인하면 된다. 과거 #1015의 테스트 결제 성공과 이번 수정본 배포 검증은 구분한다.
